# Правила работы с frontend

Корневой `AGENTS.md` и `CONTRIBUTING.md` действуют для всего проекта; этот файл дополняет их правилами интерфейса.

## Стек и исходные решения

- Использовать существующие React, TypeScript, Vite, React Router, pnpm, Tailwind CSS, `fetch` и Zustand для необходимого общего состояния. Собственные элементы дизайн-системы; Chakra UI не использовать. Версии и команды — в `frontend/README.md` и lockfile.
- Перед изменением, использующим библиотеку или инструмент, проверить закреплённую версию и соответствующую ей официальную документацию. Не обновлять зависимость по пути и не переносить API другой версии по памяти.
- Код интерфейса из Lovable сначала изучить и проверить. Переносить согласованные экраны и элементы в существующую инфраструктуру; спорный дизайн и расположение уточнять у Николая, продуктовые требования — у Андрея.

## Архитектура FSD

Начинаем с `src/app`, `src/pages` и `src/shared`. `widgets`, `features` и `entities` добавляются, когда конкретная задача или повторное использование оправдывают их. Не создавать пустые слои и папки заранее.

- `app` — запуск, провайдеры, маршрутизация, глобальные стили и общая оболочка приложения.
- `pages/<страница>` — экран и относящиеся только к нему компоненты, запросы, состояние и функции. Большой экран можно разделять внутри среза, не вынося каждый блок в отдельный слой.
- `shared` — переиспользуемые компоненты (`ui`), общий HTTP-клиент (`api`), библиотеки функций и хуков (`lib`), общие стили (`styles`); сегменты создавать по необходимости. Переиспользуемые компоненты раскладки можно хранить в `shared/ui`.
- `widgets` — крупный самостоятельный блок страницы, когда он переиспользуется или упрощает сложную страницу; `features` — пользовательские действия; `entities` — общие представления и логика предметных сущностей. Это не обязательные уровни для каждого экрана.
- Типы, DTO, хуки, функции и стили держать рядом с использующим их кодом. Выносить в `shared` только при обоснованном совместном использовании; DTO общих запросов — рядом с соответствующим API-кодом. Не вводить глобальные `types`, `hooks` или `utils` ради типа файла.
- Срез импортирует другие срезы только из нижележащих слоёв. Срезы одного слоя напрямую друг от друга не зависят; их совместную логику размещать выше или выделять общую часть ниже. `app` и `shared` состоят из сегментов: сегменты внутри одного из этих слоёв могут взаимодействовать, сохраняя обычное направление зависимостей между слоями.
- При использовании среза извне предоставлять небольшой публичный API, обычно `index.ts`; внутри среза импортировать собственные файлы напрямую, чтобы не создавать циклы. Не делать один общий barrel для всего `shared/ui` или `shared/lib`; при необходимости экспортировать отдельные элементы по отдельности. Не создавать `index.ts` в каждой папке механически.
- Не перестраивать всю существующую структуру ради нового правила. При изменении затронутого кода устранять явные нарушения в пределах задачи; крупное перемещение обсуждать отдельно.

## React и состояние

- Компонент отвечает за отображение и пользовательское действие; сложную обработку, запросы и преобразования выносить в понятные функции или хуки рядом с экраном. Не выделять обёртку, если она ничего не упрощает.
- Локальное состояние оставлять в компоненте или ближайшем общем родителе. Zustand применять для действительно общего состояния. Не хранить второй источник истины для значения, которое можно надёжно получить из уже имеющихся данных.
- Вычислять данные для отображения из props и состояния; `useEffect` использовать для синхронизации с внешними системами, а не для копирования вычисляемых значений. Действия пользователя обрабатывать в обработчиках событий. Хуки вызывать по правилам React на верхнем уровне компонента или другого хука.
- При запросах предусматривать загрузку, пустой результат, ошибки и устаревшие ответы при смене параметров или уходе со страницы. Не показывать старый результат как результат нового запуска.
- Доступность, клавиатурное управление, адаптивность, согласованность тем и видимые текстовые состояния проверять для затронутого интерфейса; оформление и расположение элементов должны соответствовать согласованному дизайну.

## TypeScript, API и читаемость

- Для описания структуры объектов предпочитать `interface`; `type` использовать, когда интерфейс не подходит, например для union, пересечений и преобразований типов.
- Не использовать `any`, принудительное приведение или `!` как замену проверке неизвестных данных. Ответ сервера — внешние данные: статический тип сам по себе не валидирует JSON. Проверять границу по единому техническому контракту; механизм runtime-валидации выбирать по задаче и не добавлять библиотеку без необходимости.
- Существующий `requestJson<T>` не проверяет структуру ответа во время выполнения. Не объявлять такой ответ проверенным только из-за `T`; обработать ошибку HTTP, сети и некорректного ответа в соответствующей части клиента.
- DTO и имена полей не выдумывать. Агенты могут подготовить и независимо проверить единый технический контракт в рамках корневых правил; синтетические примеры явно отмечать и не выдавать за реальные результаты.
- Простые тернарные выражения допустимы. Сложные и вложенные выражения, которые трудно читать, заменять на `if / else`, ранний выход или понятную комбинацию условий.
- Для отсутствующих значений предпочитать явные проверки и сужение типа, когда это упрощает чтение. `?.` и `??` допустимы, когда смысл очевиден. Не смешивать `null` и `undefined` с допустимыми `0`, `false` и пустой строкой; не подменять отсутствие денег нулём.
- Денежные вычисления остаются на backend; frontend получает и показывает строки по контракту, сохраняя различие между неизвестным значением и нулём.
- Использовать существующий помощник `classes` для объединения Tailwind-классов, когда это нужно. Общие токены и варианты компонентов не дублировать по страницам; не менять дизайн или CSS-фреймворк без согласования.
- Просматривать доступные предупреждения TypeScript, сборки, тестов и редактора для затронутого кода; исправлять применимые предупреждения и обоснованные предложения по читаемости. Если диагностика IDE недоступна, не утверждать, что она проверена: использовать доступные командные проверки и указать ограничение. Не упрощать код автоматически, если меняется смысл.
