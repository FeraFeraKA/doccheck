# Правила тестирования frontend

Действуют общие правила проекта и `frontend/AGENTS.md`. Здесь располагаются тесты frontend, включая браузерные сквозные сценарии; тесты backend находятся в `backend/tests/`.

## Что проверять

- Не покрывать юнит-тестами всё подряд. Писать их для важной логики получения и обработки данных от backend, формирования и отправки запросов и других преобразований, влияющих на поведение продукта. Проверять результат и ошибки, а не внутреннее устройство функции.
- В том числе проверять, когда это затрагивается изменением: отсутствие значения отдельно от нуля, передачу параметров запроса, преобразование ответа, состояния и ошибки. Денежные расчёты остаются на backend.
- Интеграционными тестами проверять взаимодействие частей интерфейса: действия пользователя, состояния загрузки и ошибки, фильтры, выбор показателя и открытие источника. Достаточно нескольких значимых пользовательских сценариев; дополнять их по мере появления нового поведения и исправления ошибок.
- Для основных сценариев предусмотреть несколько полных пользовательских flow: от действия пользователя до отображения результата. Интерфейсный flow с моками и сквозной проход через настоящий API, worker и обработку — разные проверки; браузерные сквозные тесты размещать здесь, когда компоненты готовы.

## Как проверять

- Использовать синтетические или явно разрешённые локальные данные; публичный CI использует только разрешённые синтетические фикстуры. Независимые эталоны не включать в тестовый runtime. Моки явно обозначать и не выдавать за настоящую обработку.
- Использовать Vitest для unit-тестов, React Testing Library для тестирования React-компонентов по необходимости и Playwright для браузерных сценариев. Настроить их вместе с приложением, закрепить зависимости и документировать проверенные команды. Другие зависимости согласовывать с Николаем.
- Запускать доступные затронутые тесты, проверку типов и сборку. Для визуальных и интерактивных изменений дополнительно проверять сценарий в браузере, если возможно. В отчёте фиксировать реальные результаты и ограничения.
- Не утверждать, что тесты или реальная интеграция прошли, если они не запускались. Не изменять ожидаемый результат только ради прохождения проверки.
