# TypeScript frontend

Владелец направления — Николай. Интерфейс поддерживает загрузку пакета,
историю, состояния заданий, сохранённые результаты и просмотр источников.
HTTP-маршруты и результат описаны в [общем контракте](../contracts/README.md).

## Согласованный стек

- React, TypeScript и Vite; React Router для маршрутизации.
- Zustand для общего состояния интерфейса, когда оно необходимо нескольким частям приложения. Локальное состояние остаётся в компонентах React; серверные данные не дублируются без причины.
- Встроенный `fetch` и общий API-клиент для запросов, обработки ошибок и загрузки файлов. Клиенты рабочих маршрутов используют контракт NRT-13.
- Tailwind CSS, общие стили и токены, собственные переиспользуемые компоненты дизайн-системы. Chakra UI не используется. Удобный способ объединения классов и варианты компонентов выбираются при реализации.
- pnpm — менеджер пакетов; версия pnpm и зависимости закреплены в `package.json`, дерево зависимостей — в `pnpm-lock.yaml`.
- Vitest для unit-тестов, React Testing Library при проверке React-компонентов и Playwright для браузерных сценариев. Принципы описаны в `tests/AGENTS.md`.

## Установка и запуск

Поддерживаемые версии Node.js указаны в `package.json`; для разработки и CI закреплена версия из `.node-version` — 26.12.1. Версия pnpm задаётся полем `packageManager` в `package.json` — 12.14.0. Из папки `frontend`:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Перед запуском UI подготовить PostgreSQL, применить миграцию и запустить API и отдельный worker по [инструкции backend](../backend/README.md). Затем открыть адрес, выведенный Vite.

Vite проксирует `/health` и `/api` на локальный `http://127.0.0.1:8000`. При другом порте API задать `DOCCHECK_API_TARGET` в окружении процесса Vite:

```sh
DOCCHECK_API_TARGET=http://127.0.0.1:8010 pnpm dev
```

В PowerShell:

```powershell
$env:DOCCHECK_API_TARGET = 'http://127.0.0.1:8010'
pnpm dev
```

Для [запуска через Compose](../README.md#запуск-каркаса-через-docker-compose)
frontend собирается по `pnpm-lock.yaml`. nginx отдаёт собранные файлы и
проксирует `/health` и `/api/` на внутренний сервис `api` с того же origin.
Порт хоста по умолчанию 8080, доступ только через loopback. Для Compose
не нужно запускать Vite или задавать `DOCCHECK_API_TARGET`.

## Проверки

```sh
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm exec playwright install chromium --only-shell
pnpm test:e2e
```

Chromium устанавливается один раз перед браузерными проверками; их сервер запускается автоматически на `127.0.0.1:4173`. Для интерактивного запуска Vitest доступна команда `pnpm test:watch`. Component-тесты и локальные браузерные сценарии подменяют рабочий API. `smoke.spec.ts` проверяет, что старая ссылка `/system-status` ведёт в мастер проверки. В [.github/workflows/compose.yml](../.github/workflows/compose.yml) GitHub Actions отдельно проверяет рабочий Compose-стек и синтетическое задание через API.

Общий `requestJson<T>` возвращает JSON с указанным типом. Клиенты рабочих маршрутов проверяют полученные поля статуса, результата и источника.

GitHub Actions настроен в `.github/workflows/frontend.yml`: при push, pull request и ручном запуске он устанавливает зависимости по lockfile, запускает Oxlint для TypeScript и React, проверяет типы, тесты, сборку и браузерный smoke-тест. Фактический результат Actions можно подтвердить только после запуска на GitHub. Настройки Oxlint находятся в `.oxlintrc.json`. Диагностика редактора зависит от установленных расширений.

В PR #2 использовались npm и `package-lock.json`. При переносе нужных элементов макета использовать существующие настройки pnpm и не добавлять второй lockfile.

Денежные вычисления выполняются в Python. Интерфейс отображает строки из
результата, различает ноль и отсутствие значения.

## Загрузка и история проверок

1. Откройте `/` или `/checks/new`, выберите один файл КФЗ и добавьте первичные
   документы. Допустимы PDF, DOCX, XLSX и PNG. Договор, период и адрес строки
   поступают из последующей обработки пакета.
2. Дождитесь сообщения «Пакет загружен» и нажмите «Запустить проверку».
   Пока идёт передача и подтверждение, кнопка недоступна. Проверка появляется
   в очереди под формой только после запуска. При обработке очередь показывает
   состояние сервера и полосу без процента, если сервер ещё не сообщил счётчик.
   Готовая карточка открывает результат. До подключения обработчика пакет ждёт
   в очереди. Повтор запуска использует тот же ID пакета.
3. В `/checks` доступна история сохранённых проверок. Карточка показывает
   состояние, прогресс при наличии данных и ошибки. Если обработка завершилась
   и сохранила результат, карточка загружает его отдельно.
4. Нажмите глазик или откройте файл из «Документов», чтобы посмотреть
   документ с начала. Можно переключать листы XLSX и страницы PDF, читать
   DOCX и PNG и переходить к точному адресу из показателя. В документе
   подсвечены сохранённые адреса, оригинал можно скачать.
5. В «Документах» доступны «Изменить комплект», раздел «Исключения»
   и «Скачать XLSX» под таблицами. Изменённый комплект создаёт новую проверку,
   его исходная версия остаётся в истории.
   Прямой маршрут `/checks/:id/conclusion` также открывает выгрузку сохранённой проверки.
6. «В архив» перемещает завершённую проверку из списка в `/archive`.
   «Вернуть из архива» восстанавливает её в списке. Результат и ссылки
   сохраняются. Для ридеров и архива нужен локальный API с миграцией
   `0005_run_archive`. Для нового мастера примените также
   `0006_prepared_upload` и настройте прокси для `/api/v0/runs/uploads`
   с тем же лимитом тела, что и у `/api/v0/runs`.

Подключение рабочего адаптера относится к NRT-95, сквозная проверка
с интерфейсом — к NRT-43. Технические границы и
результаты проверок описаны в отчётах
[NRT-99](../docs/agent-runs/nrt-99.md),
[NRT-100](../docs/agent-runs/nrt-100.md),
[NRT-101](../docs/agent-runs/nrt-101.md) и
[NRT-102](../docs/agent-runs/nrt-102.md).
