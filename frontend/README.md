# TypeScript frontend

Владелец направления — Николай. Здесь будет интерфейс загрузки, статусов обработки, таблицы сверки, источников и экспорта.

Типы результата будут соответствовать единому контракту после согласования владельцами ядра и интеграции. Присланные JSON пока рассматриваются и не импортированы. Отображение фикстуры должно явно обозначать синтетический режим.

## Согласованный стек

- React, TypeScript и Vite; React Router для маршрутизации.
- Zustand для общего состояния интерфейса, когда оно необходимо нескольким частям приложения. Локальное состояние остаётся в компонентах React; серверные данные не дублируются без причины.
- Встроенный `fetch` и общий API-клиент для запросов, обработки ошибок и загрузки файлов. DTO и детали клиента зависят от согласованного контракта в NRT-13.
- Tailwind CSS, общие стили и токены, собственные переиспользуемые компоненты дизайн-системы. Chakra UI не используется. Удобный способ объединения классов и варианты компонентов выбираются при реализации.
- pnpm — менеджер пакетов; версия pnpm и зависимости закреплены в `package.json`, дерево зависимостей — в `pnpm-lock.yaml`.
- Vitest для unit-тестов, React Testing Library при проверке React-компонентов и Playwright для браузерных сценариев. Принципы описаны в `tests/AGENTS.md`.

## Установка и запуск

Поддерживаемые версии Node.js указаны в `package.json`; для разработки и CI закреплена версия из `.node-version` — 26.12.1. Версия pnpm задаётся полем `packageManager` в `package.json` — 12.14.0. Из папки `frontend`:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Перед запуском UI подготовить PostgreSQL, применить миграцию и запустить API и отдельный worker по [инструкции backend](../backend/README.md). Затем открыть адрес, выведенный Vite. Стартовая страница проверяет `/health`, создаёт явно синтетическое задание и показывает его состояния `queued → processing → completed` либо техническую ошибку `failed`. Результат помечен как тестовый; OCR, загрузка документов и настоящая финансовая сверка здесь не выполняются.

Vite проксирует `/health` и `/api` на локальный `http://127.0.0.1:8000`. При другом порте API задать `DOCCHECK_API_TARGET` в окружении процесса Vite:

```sh
DOCCHECK_API_TARGET=http://127.0.0.1:8010 pnpm dev
```

В PowerShell:

```powershell
$env:DOCCHECK_API_TARGET = 'http://127.0.0.1:8010'
pnpm dev
```

Для [запуска через Compose](../README.md#запуск-каркаса-через-docker-compose)
frontend собирается по `pnpm-lock.yaml`. nginx отдаёт собранные файлы и
проксирует `/health` и `/api/` на внутренний сервис `api` с того же origin.
Порт хоста по умолчанию 8080, доступ только через loopback. Для Compose
не нужно запускать Vite или задавать `DOCCHECK_API_TARGET`.

При потере связи во время создания или опроса задания UI показывает ошибку и отключает создание. Состояние «доступен» возвращается после успешной проверки связи. До неё виден последний известный статус задания, а после неё опрос продолжается с тем же ID. Если связь есть, но ответ на опрос некорректен, опрос можно повторить кнопкой «Обновить статус задания». Запросы ограничены пятью секундами и отменяются при уходе со страницы. Создание задания не повторяется автоматически после потери ответа: результат отправленного запроса может быть неизвестен.

## Проверки

```sh
pnpm typecheck
pnpm test
pnpm build
pnpm exec playwright install chromium --only-shell
pnpm test:e2e
```

Chromium устанавливается один раз перед браузерными проверками; их сервер запускается автоматически на `127.0.0.1:4173`. Для интерактивного запуска Vitest доступна команда `pnpm test:watch`. Component-тесты и браузерные сценарии в `smoke.spec.ts` явно подменяют API: проверяют синтетический lifecycle, ошибки сети и восстановление. Component-тесты дополнительно проверяют 503, некорректный ответ, ошибку задания и отмену запроса при уходе со страницы. Эти подмены не подтверждают интеграцию с настоящими PostgreSQL и worker; её результаты фиксируются отдельно в отчёте NRT-8.

Общий `requestJson<T>` возвращает JSON с указанным типом, но сам не валидирует его структуру. Клиент синтетического каркаса `src/pages/home/scaffoldApi.ts` запрашивает `unknown` и проверяет DTO во время выполнения, включая признак `synthetic`, допустимый статус и структуру результата. Финансовые DTO будут определены отдельно.

GitHub Actions настроен в `.github/workflows/frontend.yml`: при push, pull request и ручном запуске он устанавливает зависимости по lockfile, проверяет типы, тесты, сборку и браузерный smoke-тест. Фактический результат Actions можно подтвердить только после запуска на GitHub. Отдельный линтер пока не настроен; диагностика редактора зависит от установленного редактора и его расширений.

В PR #2 использовались npm и `package-lock.json`. При переносе нужных элементов макета использовать существующие настройки pnpm и не добавлять второй lockfile.

Выбор средств просмотра PDF, PNG, XLSX и DOCX зависит от контракта источников и будет определён при реализации. Денежная логика не переносится из Python во frontend.
