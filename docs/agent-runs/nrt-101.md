# NRT-101 — клиент чтения результата

[Задача Linear](https://linear.app/andreiakimov/issue/NRT-101/frontend-podklyuchit-realnye-rezultaty-sverki)
и связанные NRT-13, NRT-95 и NRT-97 прочитаны 13 ноября 2026 года.
База `46105e821fbee79a1a600d601cd5cb790d52f725` содержит маршрут NRT-97
и интерфейс состояния NRT-100.
Ответ 200 по OpenAPI — объект CheckResult версии 1.

## Цель и критерии Linear

Подключить таблицу и детали показателей Lovable к сохранённому результату
задания. Расхождения следует выделять сразу, сохраняя сводные значения,
причины неполноты и первичные источники. Возможные объяснения по правилам
следует обозначать как гипотезы.

- [ ] Результат по согласованному контракту отображает показатели,
  reported/expected/delta/status и доступные основания. Денежные суммы
  вычисляет backend.
- [ ] Отсутствующие значения отличаются от нуля. Причины unverified,
  частичные ошибки и исключения доступны пользователю.
- [ ] Проверены загрузка, пустой результат, ошибки и выбор показателя.
  Значимая обработка ответа API покрыта автоматическими тестами.
- [ ] Подключение к реальному результату подтверждено отдельным прогоном.
  Синтетический пример явно обозначен.

## Подготовлено

`loadFindings(runId, signal)` загружает `GET /api/v0/runs/{run_id}/findings`.
В рантайме проверяет версию, принадлежность ответа запросу, метку
синтетики и структуру отображаемых полей. В проекции `ReviewResult`
сохранены строки значений, `null`, единицы, отдельно наблюдаемая сумма,
статусы и причины. Для слагаемых сохранены суммы, ссылки на доказательства
и основания допуска. Связь от строки до первичного замечания и ошибки файла
доступна через `root_issue_id`, `file_error_refs` и `evidence_refs`. Адаптер
сохраняет признаки происхождения результата и не формирует гипотез из
текста причин. Для PDF/PNG, XLSX и DOCX проецируются адреса из результата.
Синтетическая фикстура совместима с той же проекцией.

У клиента различимы ошибки HTTP, включая ожидание результата и сбой
задания по кодам отказа 409. Код ответа прокси доступен без JSON.
Некорректный ответ 200 отклоняется. Сетевой сбой и отмена передаются
вызывающему коду. Проверку полного контракта, арифметики и согласованности
ссылок выполняет backend. Клиент валидирует отображаемую проекцию.

Карточка сохранённой проверки запрашивает результат после `completed`
или `completed_with_issues`. При ошибке загрузки результата доступен
повтор запроса за результатом с сохранением состояния и прогресса задания.
Показаны пустой результат, отчётные и ожидаемые значения, дельта и статус.
Единица измерения указана в каждой строке отдельной колонкой,
включая строки без доступных значений.
Наблюдаемая сумма при неизвестном ожидаемом значении подписана как
частичная. В выбранном показателе видны причины, основания по слагаемым,
структурные адреса и связанная ошибка первичного файла. Пометка сохранённого
синтетического результата определяется полем `synthetic` из API. Встроенный
синтетический пример открывается отдельно и работает без запросов к API.

## Проверки и продолжение

Node 26.12.1, pnpm 12.14.0. Прошли `pnpm install --frozen-lockfile --offline`,
`pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test`, `pnpm test:e2e`
и `git diff --check`. Прошли 69 Vitest и 12 Playwright. Покрыты пустой
результат, оба режима, ошибки, повтор без опроса, частичная сумма,
причины неполноты, различие нуля и `null`, разные единицы в одном результате,
исключения и выбор источника.
Дополнительный сценарий для частичной суммы прошёл `CheckJob.model_validate`.

Отдельный локальный Chromium-прогон прошёл через Vite, настоящий FastAPI
и PostgreSQL 18.4 с миграциями. В изолированную БД были сохранены два
результата, валидированных `CheckJob`, для обоих успешных терминальных
состояний. В браузере проверены GET findings, маркировка синтетики,
частичная сумма при `expected_value: null`, адрес и ошибка файла.
Это синтетический сохранённый результат. Проверка фактической обработки
зависит от NRT-95. Просмотр оригиналов относится к NRT-102.
