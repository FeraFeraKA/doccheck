# NRT-84 — подготовка экранов Lovable к подключению backend

[Задача Linear](https://linear.app/andreiakimov/issue/NRT-84/podgotovit-ekrany-lovable-k-podklyucheniyu-backend)
прочитана 13 ноября 2026 года. Техническая база — NRT-83 и HTTP-контракт NRT-13.
Проверен [исходный коммит Lovable](https://github.com/ananakimov/project-placeholder/tree/163f6367f91d9885b16685f0981290874858e955),
включая маршруты и диалог экспорта. Для проверки границ источников прочитан
разрешённый комплект из 25 файлов, включая оба README, КФЗ и изображения.

## Цель и критерии из Linear

Подготовить полученные от Андрея экраны Lovable к подключению настоящего
backend, сохранив согласованный интерфейс и явно отделив временные данные
от реальной обработки. Клиентский путь предназначен для бухгалтера.
На входе КФЗ и первичные документы. Сводные значения собирает приложение.

- [ ] После NRT-83 проверены и подготовлены экраны загрузки, состояния проверки,
  результатов, источников и экспорта в пределах действительно переданного интерфейса.
- [ ] Определены точки подключения данных и необходимые состояния загрузки,
  ошибок и отсутствующих данных. Недостающие экраны и продуктовые решения
  согласованы с Николаем и Андреем.
- [ ] Синтетический режим и его ограничения явно обозначены. Отсутствие
  значений не отображается как ноль.
- [ ] Пройдены применимые проверки и проверка экранов в браузере,
  неподключённые возможности перечислены.

## Подключение данных

| Экран | Точка подключения |
| --- | --- |
| Мастер | Хранит выбранные `File` отдельно от записей синтетического примера, различает отсутствие файлов и ошибку выбора. Для `POST /api/v0/runs` понадобятся один локальный файл КФЗ, первичные документы и обязательные параметры области из OpenAPI. Сборка multipart, повторы по ключу и обработка ответа относятся к NRT-99. |
| История | `ChecksOverview` получает асинхронную функцию `loadHistory`. В интерфейсе предусмотрены загрузка, ошибка с повтором, пустой список и поиск без совпадений. `GET /api/v0/runs` отдаёт ID, дату, статус и ошибку запуска. Договор, период, число файлов и сводные счётчики доступны в демозаписи, для рабочих записей их наличие зависит от данных. Пагинация относится к NRT-100. |
| Проверка | `CheckDetail` получает асинхронную функцию `loadRun(id, signal)`. Загрузка экрана, прогресс задания, ошибка запроса, несуществующий ID, завершённое задание без результата и сбой обработки имеют отдельные состояния. Данные завершённой проверки должны приходить из `GET /api/v0/runs/{run_id}/findings` после чтения состояния задания. Представления получают данные для отображения. Проверка ответов по контракту и опрос статуса относятся к NRT-100 и NRT-101. |
| Источники | Панель по-прежнему показывает адрес и значение из результата. Документ и фрагмент подключаются по ID задания, документа и доказательства по OpenAPI в NRT-102. |
| Экспорт | Исходный Lovable предлагает CSV, JSON и печать заключения. Текущая задача экспорта NRT-36 и OpenAPI задают XLSX результата по `GET /api/v0/runs/{run_id}/exports/xlsx`. Действия скачивания относятся к NRT-36. Отдельная сводная выгрузка требует решения команды. |

При смене ID запроса предыдущая загрузка отменяется. Ответ устаревшей
загрузки не подставляется на экран другой проверки. Фикстура в текущем
маршруте явно синтетическая. Суммы приходят строками. Ноль отображается
числом, отсутствие значения — прочерком. Перенесённый интерфейс сохраняет
пометку о гипотезах и показывает готовый синтетический результат отдельно
от выбора файлов.

Форма выбора номера договора, периода и адреса строки зависит от ответа
[в NRT-13](https://linear.app/andreiakimov/issue/NRT-13/kontrakt-api-i-moki-dlya-fronta#comment-0041307d-969a-4511-9e4e-ca96f0638ca6).
Реальные результаты, оригиналы и фрагменты, экспорт XLSX и записи журналов
требуют последующих задач.

## Проверки

- Node 26.12.1, pnpm 12.14.0. Прошли `pnpm install --frozen-lockfile --offline`,
  `pnpm typecheck`, `pnpm build` и `git diff --check`.
- `pnpm test` — 17 тестов. Новый набор проверяет загрузку, ошибку и повтор,
  пустую историю, нулевой прогресс, отсутствие результата, сбой обработки
  и защиту от запоздавшего ответа при смене ID.
- `pnpm test:e2e` — 7 сценариев Chromium, включая выбор и валидацию файлов,
  отсутствующую проверку и поиск, а также прежний синтетический путь,
  видимость расхождений на 320/390 пикселях и переход к источникам.
- Браузерный прогон относится к синтетике и подменам. Рабочий API,
  обработчик и выгрузка в этом прогоне не использовались.
