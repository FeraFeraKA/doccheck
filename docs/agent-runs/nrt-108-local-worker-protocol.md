# NRT-108 — синтетическая очередь для воркера на компьютере

[NRT-108](https://linear.app/andreiakimov/issue/NRT-108/razvernut-demo-doccheck-na-vercel-i-render)
требует отдельно проверенный Preview на синтетике, с документами и проверяемым
состоянием API. [NRT-95](https://linear.app/andreiakimov/issue/NRT-95/podklyuchit-ml-adapter-k-worker-i-sohraneniyu-rezultata)
задаёт сохранение результата воркера, идентичность входных файлов и отделение
статуса выполнения от предметных выводов. Этот срез выполняет протокол между
локальным воркером и API. Для результатов есть отдельный серверный вход Preview.

## Локальная проверка

Используйте отдельный PostgreSQL, каталог файлов и API на loopback. API требует
`DOCCHECK_PUBLIC_DEMO=1` и `DOCCHECK_HOSTED_WORKER_SHA256` с SHA-256 случайного
секрета длиной не менее 32 ASCII-символов. При пустом хеше воркерные маршруты
отключены. Сам секрет передаётся только процессу воркера в переменной
`DOCCHECK_HOSTED_WORKER_TOKEN`. Он не передаётся в параметры URL и не включается
в браузерную сборку. У API и воркера остаются обычные локальные зависимости.

1. Примените миграции через `uv run --project backend --locked alembic -c backend/alembic.ini upgrade head`.
2. Подготовьте заведомо синтетические XLSX КФЗ и DOCX. Манифест должен содержать
   `synthetic: true`, `report: {name, sha256}` и `documents: [{name, sha256}]`.
   Пин самого манифеста получают из проверенного артефакта, а не принимают из
   пользовательской загрузки. Файлы лежат рядом с манифестом под простыми именами.
3. Из корня репозитория поместите пакет в очередь через
   `uv run --project backend --locked python -m doccheck_backend.hosted_seed PATH MANIFEST_SHA256 REQUEST_UUID`.
   Команда доступна оператору. Она сверяет хеши и атомарно регистрирует
   допуск пакета и задание. Повтор с прежним UUID сохраняет исходное задание
   при совпадении с пакетом. API произвольной загрузки по сети закрыт.
4. Запустите API в выбранном окружении. На компьютере воркера запустите
   закреплённую Ollama по [инструкции v3.2](../../bench/e2e_v32_20261114/README.md).
   Затем из корня репозитория выполните:

   ```sh
   uv run --project backend --locked --with-requirements bench/e2e_v32_20261114/requirements.txt python -m doccheck_backend.hosted_worker --origin http://127.0.0.1:18037 --processor doccheck_backend.v32_adapter:process --once
   ```

   Для удалённого API используется явный HTTPS-origin. Запросы воркера не
   перенаправляются и не наследуют системный HTTP-прокси. Ollama принимает
   только локальные вызовы, а воркер не слушает сеть.

## Границы

Протокол допускает максимум восемь первичных документов, по 2 МиБ каждый,
и результат до 1 МиБ. Срок текущей аренды 60 секунд, воркер запрашивает
продление раз в 15 секунд. По истечении аренды следующий захват выбирает
повтор, а после трёх попыток или общего дедлайна в 15 минут фиксирует отказ.
Старый идентификатор не может продлить или завершить новую попытку.
После завершения повтор идентичного результата не меняет запись.
При потере соединения вычисляющая задача может завершиться в локальном
потоке, но её просроченный результат не будет сохранён. Временные файлы
удаляются после завершения или отказа.

Выбран один доверенный воркер и один ротируемый секрет для отдельного
синтетического стенда. Обычный публичный режим без настроенного хеша
блокирует доступ к очереди.

## Закрытый доступ к результатам

API включает браузерные чтения, когда заданы `DOCCHECK_HOSTED_VIEWERS`
с JSON-объектом `{"UUID участника":"sha256 приглашения"}` и
`DOCCHECK_HOSTED_SESSION_KEY` с отдельным случайным ключом из 32 байт
в hex. Приглашение получает сам участник. По HTTPS браузер отправляет его
JSON-запросом `POST /api/preview/v1/session` с телом `{"token":"..."}`.
Ответ устанавливает подписанную одночасовую `Secure` `HttpOnly` cookie.
Информация о приглашениях и секрет воркера остаются вне сборки браузера.
Удаление приглашения из конфигурации или замена его хеша отзывают
существующую сессию после обновления конфигурации API.

При операторском допуске `--viewer UUID` прикрепляет конкретного участника.
Затем `GET /api/preview/v1/runs` и `GET /api/preview/v1/runs/{run_id}`
показывают только его задания. Структуры `/findings`, `/documents/{id}`,
`/fragments?evidence_id=...`, `/fragment-preview?evidence_id=...` и
`/exports/xlsx` соответствуют локальному API. У чужого запуска и неизвестного
ID одинаковый ответ 404. Владелец определяется сессией, а не параметром
запроса. Этот срез только читает ранее допущенные пакеты. Публичный
документный API продолжает блокировать отправку произвольных файлов.

Отдельная сборка `frontend/hosted-preview.html` показывает вход по
приглашению, ход допущенной проверки и ссылки на JSON и XLSX. Render
готовит один встроенный синтетический пакет на участника при старте
выделенного API. Параметры реальных файлов или путь к пакету не принимаются
из запроса. Для удаления пакетов после демо оператору понадобится отдельно
согласованный срок хранения.

Для отдельного проекта Vercel выберите Root Directory `frontend`.
В настройках Preview задайте `DOCCHECK_HOSTED_PREVIEW=1` и
`DOCCHECK_PREVIEW_RENDER_ORIGIN` с точным HTTPS-origin отдельного API Render.
Конфигурация проксирует только `/api/preview/v1`, сохраняет cookie на общем
origin и запрещает кеширование ответов. Откройте доступ лишь приглашённым
участникам. Секреты из Render передавать в Vercel не требуется.

В Render при согласованной публикации используйте отдельный Blueprint
`render.hosted-preview.yaml`. Он описывает бесплатные API и PostgreSQL.
В образ включены только два синтетических файла, закреплённые хешем
манифеста из кода. При сбросе эфемерного каталога API восстанавливает
оригиналы из образа под сохранёнными ID. Размеры, форматы и SHA-256
проверяются повторно. Отсутствующие и повреждённые файлы восстанавливаются
из проверенного образа. Ключ стартового задания включает SHA манифеста.
При обновлении пакета создаётся новое задание. Прежние результаты остаются
в PostgreSQL, а старые версии оригиналов доступны после перезапуска только
если соответствующие версии пакета входят в образ. Текущая поставка
содержит одну версию.

Если бесплатный слот PostgreSQL занят, можно выбрать отдельный конфиг
`render.hosted-preview-shared-db.yaml`. Он создаёт бесплатный Web Service
без ресурса БД. Для его запуска администратор отдельно создаёт логическую
БД и отдельный логин с одинаковым именем `doccheck_hosted_preview` в том
же экземпляре PostgreSQL. Логин владеет только новой базой. Не используйте
Render-managed ротацию, которая делает нового пользователя default,
и не меняйте роли, привилегии и DSN публичного демо.

Передайте новому сервису `DOCCHECK_HOSTED_SHARED_DATABASE_URL` с внутренним
адресом в том же регионе, именем новой БД, выделенным логином и его паролем.
`DOCCHECK_HOSTED_PUBLIC_DATABASE_NAME` содержит фактическое имя существующей
логической базы публичного демо, не имя ресурса в Dashboard. Параметр
`DOCCHECK_RENDER_DATABASE_URL` предназначен только для отдельного экземпляра
и не используется одновременно с shared-настройками. Перед миграциями
API проверяет имена, действующего пользователя, владельца и отсутствие
привилегированных прав через транзакцию PostgreSQL `READ ONLY`. Обязателен
отдельный логин без членства в других ролях; администратор дополнительно
проверяет отсутствие доступа к таблицам публичного демо у нового логина.
Разные логические базы разделяют права и содержимое, но используют общие
лимиты экземпляра. План и хранение обеих БД согласуются перед запуском.
[Бесплатные лимиты Render](https://render.com/docs/free#free-postgres) ·
[Несколько логических БД](https://render.com/docs/postgresql-creating-connecting#adding-multiple-databases-to-a-single-instance) ·
[Ротация пользователей Render](https://render.com/docs/postgresql-credentials).

Если администратор не может подготовить такое разделение или недоступен
бесплатный Web Service, облачный Preview остаётся выключенным.
Перед открытием проверьте ограничение
обращений и срок хранения. Для отката отключите
Preview, остановите выделенную очередь и отзовите её секрет и приглашения.

[Render Blueprint](https://render.com/docs/blueprint-spec) ·

## Проверки

Проверены HTTP-протокол и сохранение через отдельный PostgreSQL, включая
скачивание оригиналов, проверку их SHA-256, устаревшую аренду, повтор
завершения, отклонение неверного секрета и запрет публичной загрузки.
При кратковременном сбое воркер повторяет загрузку до трёх раз.
После исчерпания сетевых попыток аренда истекает и позволяет выдать
пакет повторно, без немедленного терминального статуса.
При истечении последней попытки или общего срока обычное чтение состояния
в Preview сохраняет терминальную ошибку даже при недоступности компьютера
воркера. В выделенном Preview закрыты также старые маршруты
`/api/synthetic-jobs`; обычное публичное демо продолжает их обслуживать.
Для показа на бесплатном Render используйте запуск воркера с `--once`.
Постоянный опрос предотвращает засыпание Web Service и расходует общие
бесплатные часы workspace.
Управляемый адаптер в тесте явно синтетический, результат помечается как
синтетический по источнику пакета независимо от флага в ответе воркера.
Тест Preview проверяет параметры cookie и общий отказ во всех маршрутах
с чужим ID. Chromium через изолированный HTTPS-прокси открыл настоящий
Preview, вошёл по приглашению, увидел только свой синтетический результат
и сохранил сессию после обновления. На отдельной БД с настоящей локальной
Qwen воркер обработал встроенный XLSX и DOCX для двух участников через
исходящий HTTP. Оба результата сохранили закреплённую версию модели,
9000.00 частичного подтверждения и по шесть доказательств. Полный вызов
воркера занял 2,54 и 2,08 секунды. Chromium затем прочитал один из этих
результатов по приглашению через локальный HTTPS-прокси.
Прошли 452 backend-теста с PostgreSQL,
146 frontend-тестов, lint, typecheck и сборка отдельной страницы. Проверка
конфигураций пройдена по официальным сохранённым схемам. Деплой на Vercel
и Render не выполнялся. Полноценный пользовательский маршрут отправки
допущенного примера и переходов между документами относится к отдельной
итерации интерфейса. Эта страница служит для проверки выдачи результатов.
