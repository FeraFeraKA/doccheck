# NRT-94 — вызов модуля идентификации из адаптера наблюдений

[NRT-94 в Linear](https://linear.app/andreiakimov/issue/NRT-94/realizovat-adapter-vyzova-gotovogo-ml-modulya)
и NRT-93 прочитаны 14 ноября 2026 года. Основа —
[согласованная граница NRT-93](../ml-module-boundary.md).

## Вызов

Вызов `identify_documents(documents, synthetic=...)` принимает готовые
`ObservedDocument` с SHA-256, локальными путями и адресными наблюдениями.
Каждое наблюдение хранит текст, существующий `Locator` и происхождение
`native` или `ocr`. Область координат и инвентарь листов предоставляет
источник наблюдений для той же версии файла. Адаптер проверяет геометрию,
сопоставляет тип адреса с форматом и сверяет лист с переданным инвентарём.
Формат оригинала и правильность полученного текста остаются
ответственностью извлечения.

Адаптер вызывает установленный `doccheck_ml.process_documents` напрямую,
последовательно и без HTTP. Любое OCR-наблюдение переводит документ в
`scan` для модуля, а исходное происхождение каждого фрагмента сохраняется.
Пути передаёт доверенная локальная сторона. Модуль сверяет байты с SHA-256
и сообщает о недоступных или изменённых файлах по ID. При отсутствии модуля
адаптер возвращает типизированную ошибку доступности. Установка пакета в
контейнер и вызов из реального worker относятся к NRT-95.

## Результат

Суммы, реквизиты, типы и стороны остаются кандидатами. Адрес возвращается
только при однозначном совпадении доказательства с переданным наблюдением.
Структурные адреса DOCX хранятся рядом с наблюдением, поскольку текущий
модуль принимает для DOCX только текст. Неоднозначный обратный поиск
помечается `source_ambiguous`. Сохраняются версии, признак синтетики,
ошибки файлов, признаки ручной проверки, конфликты, проверенные группы
одинаковых SHA-256 и пары для дальнейшего рассмотрения.

Адаптер не присваивает статусы финансовой сверки. Предложения модели без
ссылки на наблюдение не получают адрес. Решения о сумме, её роли, периоде,
статье и полноте останутся за соответствующими правилами ядра.

## Проверки

На базе `1565431e20b3b4015e2c0f9dd39c8faf8231fb08` прошли 12 целевых тестов.
Реальный публичный вызов выполнен с синтетическими файлами и наблюдениями,
в том числе со смешанным происхождением, изменённым и отсутствующим файлом,
одинаковыми байтами, структурным DOCX и точным XLSX-адресом. Тест
несовпадения SHA в ответе использовал подмену результата.

Прошли Ruff check/format и проверка lockfile. Полный прогон без БД дал
133 успешных теста и 43 явных пропуска PostgreSQL-сценариев. Код Qwen,
веса, обучение и рабочий pipeline не использовались.

## Повторное ревью #39

Источник выбранного номера теперь привязывается через совпадающее
документное чтение. При конфликте модельный кандидат сохраняется без
адреса, а адрес исходного номера остаётся доступен. Ответ модуля с явно
указанным исполнителем может не содержать список альтернатив.

Составной кандидат получает адреса только при однозначном сопоставлении
всех наблюдений с одним способом извлечения и подтверждённой смежности
по номерам строк одной страницы или единичным ячейкам одного листа.
Простой порядок наблюдений, bbox без строки и структура DOCX, которую
модуль не представляет, смежность не доказывают. Кандидат при этом
сохраняется с `source_ambiguous`.

Для суммы и номера модуль может объединить независимые совпадающие
чтения в общий список. Адаптер сохраняет их отдельные адреса, когда
каждая исходная строка содержит полное совпадающее чтение. Если ответ
смешивает подтверждённые и неполные строки и не сохраняет их группировку,
сохраняются только доказуемые адреса с пометкой неоднозначности.

Одиночный маркер «№» без роли в собственной строке требует
смежного адресного заголовка. Сам порядок наблюдений и общая
страница с удалёнными рамками такой связи не подтверждают.

Дополнительные регрессии через реальный модуль проверяют самостоятельные
чтения с единицей в заголовке «Итого, руб.», номер акта рядом с отдельно
подписанным номером договора и сумму на строке после смежного маркера
«Итого:». Сохранены адреса всех частей, необходимых для полного чтения.

`IdentityCandidate.provenance` хранит адресные наблюдения, которые модуль
вернул именно для этого чтения. `sources` содержит наблюдения, связь
которых со значением и ролью удалось дополнительно подтвердить.
Если роль или группировка не установлены, `source_ambiguous` сохраняется,
а исходные адреса доступны в `provenance` для проверки. Они сами по себе
не подтверждают реквизит. При конфликте предложения модели и номера
документа модельный кандидат не получает чужие ссылки даже в `provenance`.

Если публичный ответ передал только отдельное «№ 412», однозначный
смежный заголовок «Акт» становится дополнительным адресом в `sources`.
`provenance` по-прежнему отражает именно ответ модуля. В случае
«Номер акта:» и «№ 412» сам модуль вернул оба адреса, поэтому они
присутствуют в обоих полях. Без однозначной связи остаётся запрос проверки.

При конфликте ИНН исполнителя выбранное значение остаётся `null`.
Адаптер сохраняет отдельные адресные чтения только из возвращённого
модулем `tax_id_evidence`, вместе с флагом конфликта. ИНН покупателя
в эту группу не попадает. Чтение сохраняет исходные цифры и не
устанавливает принадлежность реквизита контрагенту.
