# NRT-39 — ограничение времени обработки document-worker

[Задача Linear](https://linear.app/andreiakimov/issue/NRT-39)
прочитана 14 ноября 2026 года. Проверен
`6e1000ad6cc26f4099b777e1f3a9c3ebc6da89f8`. Этот срез касается
критерия ограничения времени обработки. Ошибки отдельных файлов,
продолжение обработки пакета и влияние на полноту проверяются отдельно.

## Текущее поведение

- `run_document_worker` удерживает advisory lock на физическом сеансе
  PostgreSQL. Обработчик запускается синхронно. Пока соединение живо,
  второй worker не может начать работу той же очереди.
- При физической потере сеанса PostgreSQL освобождает lock независимо
  от жизни обработчика. Следующий владелец помечает прерванную запись
  как failed и может забрать следующее задание до выхода прежнего
  обработчика. Старый worker проверяет сеанс перед записью, поэтому
  отработавший позже результат не сохраняется. Это воспроизводит
  существующий `test_disconnect_leaves_recovery_to_next_owner`.
- CLI перехватывает `KeyboardInterrupt`. Отдельного обработчика POSIX
  SIGTERM нет. На Windows `Popen.terminate()` использует
  `TerminateProcess`. Тайм-аут ожидания потока не прекращает
  выполняющийся callable. Убийство одного дочернего процесса
  не завершает произвольных потомков.
  [Документация Python subprocess](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen.terminate)

## Проверки

Windows, Python 3.12.12 и изолированный PostgreSQL 18.4.
`uv run --frozen pytest -q tests/test_run_worker.py` — 19 прошли.
Покрыты удержание очереди, потеря сессии, восстановление после гибели
CLI и переходы сохранённого задания. Отдельная синтетическая проба
`subprocess.run(timeout=0.7)` на Windows дождалась падения прямого
дочернего процесса. Его потомок записал маркер спустя 1,2 секунды.
Оба процесса использовали только временный каталог. PostgreSQL
остановлен, порт 55439 освобождён. Linux и Docker на этом хосте
для прогона недоступны, платформенные механизмы сверены по документации.

## Вариант реализации

Выделить исполнение одной попытки в управляемое дочернее дерево с
ограниченным IPC для входа и результата. Держать чтение/запись
состояния и advisory lock в супервизоре, не передавать сеанс и
учётные данные БД исполнителю. На успешном пути принять результат
после подтверждённого завершения дерева, валидации контракта и
проверки сеанса владельца.

При тайм-ауте или управляемой остановке запретить приём результата,
завершить дерево и дождаться отсутствия активных процессов. Только
после подтверждения записать безопасную техническую ошибку и переходить
к следующей попытке или закрывать сеанс. Для Windows подходит Job Object
с закрытием всех процессов при утрате контролирующего дескриптора
и запретом breakaway. Для Linux нужен проверенный контейнер или
выделенная cgroup v2 с завершением всех процессов и проверкой
`populated=0`.
[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
[Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

Физическую потерю сеанса нельзя исправить порядком операций внутри
worker: PostgreSQL освобождает lock сам. Если нужно исключить
перекрытие попыток при потере сеанса или гибели супервизора, проверка
завершения прежней изоляции должна быть доступна и новому владельцу.
Например, очередь обслуживает внешний супервизор с единственным
живым исполнителем и подтверждением остановки, а незавершённая
попытка ссылается на конкретное поколение этого исполнителя. Один
lease по времени не доказывает отсутствие старого процесса.

Предлагаемый критерий будущего прогона: залипший обработчик и его
потомок, тайм-аут и SIGTERM на Linux, остановка родителя на Windows,
разрыв сеанса PostgreSQL во время работы, запоздавший результат
и успешное следующее задание. Для каждого сценария отдельно проверяются
завершение дерева и отсутствие устаревшей записи.

Рабочий CLI оставлен без нового тайм-аута до выбора среды запуска
с нужной гарантией. Вопрос владельцу интеграции: требуется ли одинаковая
гарантия завершения всего дерева для нативной Windows и Linux Compose
или можно первой поддержать Linux с проверенным контейнерным
супервизором? Рекомендация — начать с одной подтверждённой конфигурации
и явно ограничить остальные режимы.
