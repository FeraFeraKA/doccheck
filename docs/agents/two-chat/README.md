# Один компьютер: исполнитель и независимый ревьюер

Этот режим включается по поручению пользователя и работает отдельно от [ночного регламента](../nightly/README.md). На одном устройстве открыты два чата: **исполнитель** ведёт очередь и делегирует независимые задачи frontend, API и backend интеграции; **ревьюер** ведёт очередь независимого ревью PR. В каждом чате можно запустить до трёх субагентов: исполнитель назначает по одному на задачу, ревьюер — по одному на PR. Отдельного третьего чата-координатора нет: каждый основной чат координирует своих субагентов. Исполнитель не ждёт завершения ревью и продолжает другие независимые задачи.

Порядок не запускает чаты и сам по себе не гарантирует доставку сообщений, продолжение завершённого чата или наличие трёх свободных слотов. Фактический предел задаётся доступными инструментами и настройками каждого чата; если слотов меньше, использовать доступные и держать остальное в очереди. Подробнее: [официальная документация Codex о субагентах](https://learn.chatgpt.com/docs/agent-configuration/subagents). Ночной запуск NRT-90, его протокол и сохранённое состояние не используются для этого режима и не изменяются.

## Параллельность и изоляция

- Исполнитель выбирает до трёх **готовых и независимых** задач. На каждую — свой субагент, ветка, PR и рабочий каталог. Не запускать две задачи с неразрешёнными зависимостями или конкурирующими правками общего контракта, миграции либо других общих файлов. Для частично пересекающейся работы заранее установить границы; при сомнении выполнять изменения последовательно.
- По разрешению Николая рабочие копии этого режима размещаются **внутри основной папки** `doccheck/.worktrees/`, например `.worktrees/nrt-123`. Этот путь исключён из Git и Docker-контекста. Перед использованием проверить состояние основной копии, выбранной ветки, каталога и `git worktree list`. Существующую работу не заменять и не удалять. Если пользователь отдельно требует одну рабочую копию без worktree, не создавать их: параллелить только чтение и ревью, а запись в общую копию вести по одной задаче.
- Создание и удаление worktree, резервирование имён веток и слияние координирует основной чат исполнителя последовательно. Ревьюер согласует с ним выделение каталогов для проверок, если они необходимы, чтобы не гоняться за одним путём или одновременно менять общие метаданные Git. Каждому субагенту передать NRT-ID, цель и критерии, явный путь его worktree, ветку, base SHA, область файлов и ожидаемый результат. Выполнять Git-команды в своём worktree, не переключать общую копию или чужие ветки. Только автор назначенной задачи меняет её файлы и коммитит её изменения. Перед удалением своего worktree убедиться, что там нет нужных или чужих изменений; не применять принудительную очистку.
- Ревьюер запускает отдельного субагента на каждый PR и конкретную пару base/head, не более трёх одновременно. Для независимого контекста передавать ссылку на PR, задачу и критерии, SHA, применимые инструкции и результаты проверок, но не историю рассуждений автора. Субагент читает diff и исходники на фиксированных версиях; не меняет рабочие каталоги исполнителей. Если проверка требует записи, основной чат ревьюера согласует отдельный временный каталог внутри `.worktrees/` или явно отмечает невозможность проверки. Путь и состояние каталога проверяются до использования.
- Субагенты ревью возвращают выводы основному чату ревьюера. Тот сверяет вердикт с актуальным PR и задачей, публикует разрешённый отзыв и уведомляет исполнителя. Дубликат сообщения о той же паре не запускает повторную проверку, которая уже идёт или завершена. После устранения блокера, недоставшей проверки или появления новых существенных сведений ту же пару можно проверить повторно; новая версия или изменившиеся критерии также требуют актуализации проверки.
- Worktree разделяют файлы, ветки и Git-индексы, но используют общую базу Git-объектов и не являются границей доступа. Субагенты имеют доступ к окружению родителя; инструкции не заменяют изоляцию закрытых данных по `docs/data-policy.md`.
- Рабочие каталоги не изолируют порты, контейнеры, базы данных, тома, GPU и фоновые процессы. Единый распределитель таких ресурсов для **обоих чатов** — основной чат исполнителя. До запуска проверки он резервирует конкретный ресурс для задачи или PR; основной чат ревьюера запрашивает его и ждёт явного подтверждения по разрешённому каналу. По завершении владелец проверки сообщает об освобождении; время ожидания само по себе не освобождает занятый ресурс. При недоступной связи ревьюер продолжает независимую проверку, но не запускает потенциально конфликтующий тест и указывает ограничение. Если изоляция не подтверждена, зависящие от ресурса проверки идут последовательно. Останавливать можно только процессы и контейнеры, запущенные для своей проверки.
- В текущем проекте Playwright использует фиксированный порт `4173`, поэтому browser-тесты из разных worktree запускаются по очереди, пока порт не станет настраиваемым. Compose использует фиксированные теги `doccheck-backend:local` и `doccheck-frontend:local`: разные имена Compose-проектов и портов сами по себе не изолируют образы. Сборки и прогоны Compose должны идти по очереди от сборки до остановки своего стека, если отдельные теги, порты и тома не настроены и не проверены. Тестовую БД и другие общие ресурсы также изолировать или резервировать. Не выдавать результаты другого worktree за проверку своей версии.

Пример создания отдельной задачи из корня `doccheck` после проверки состояния и доступности имени ветки (заменить номер и тему на нужные):

```sh
git fetch origin
git worktree add -b nrt-123-short-topic .worktrees/nrt-123 origin/main
```

Все проверки, коммит и push задачи выполняются из назначенного каталога. Один и тот же локальный каталог нельзя одновременно переключать между ветками. Изоляция не устраняет зависимости: пока нужное изменение не попало в согласованную базу, зависимую задачу не объявлять готовой к параллельной реализации.

## Границы работы

- Исполнитель работает над frontend, API, хранением, жизненным циклом backend worker и интеграцией по задачам своей зоны ответственности. Здесь «исполнитель» — чат разработки; backend worker — процесс приложения.
- ML, OCR, извлечение и внутренняя обработка документов остаются направлением Семёна. Не брать и не переопределять его задачи, не изменять модель, веса или алгоритмы без отдельного согласования. Интеграционная задача Николая допустима по своему актуальному scope, если нужная граница и зависимости доступны; подготовку тестовой подмены не выдавать за реальный вызов. Вопросы на стыке направлений передавать владельцам по `AGENTS.md`.
- Linear — источник постановки, владельца, критериев, зависимостей и статуса; GitHub — источник веток, PR, проверяемых версий, замечаний и CI. Сверять оба: статус задачи может отставать от фактического слияния. Не менять владельцев задач и не объявлять их принятыми из-за PR. Синтетический результат, незавершённые API и ограничения модели явно обозначать.
- Выполнять корневой и вложенные `AGENTS.md`, `CONTRIBUTING.md` и `docs/data-policy.md`. При передаче задачи ставить `In Review` и метку `review`. Если пользователь явно разрешил автослияние в этом режиме, исполнитель может объединять собственные PR в `main` после двух независимых ревью и проверок ниже. `Done` и деплой остаются человеку; техническое ревью и merge не заменяют предметную приёмку.

## Запуск двух чатов

1. Пользователь открывает два разных чата в проекте DocCheck на одном устройстве. Он явно выбирает этот режим, задаёт допустимую очередь или поручает исполнителю выбирать готовые задачи frontend/backend в Linear, а также указывает целевую базу PR. По умолчанию база — `main`. Если он хочет автоматическое слияние, явно разрешает исполнителю объединять собственные PR при выполнении условий ниже. Если другие чаты или люди уже ведут задачи или редактируют рабочую копию, сначала согласовать границы и сохранить их работу.
2. Пользователь даёт каждому чату ссылку или идентификатор второго и **явно разрешает сообщения в конкретный чат**: исполнителю — отправлять запросы на ревью, ревьюеру — возвращать результаты исполнителю. Для публикации отзывов в GitHub пользователь отдельно включает её в поручение ревьюеру. Не создавать новые чаты или отправлять сообщения без такого разрешения. Если сервис не позволяет установить получателя или права, использовать ручную передачу пользователем.
3. Ревьюер получает роль и инструкцию ниже. Исполнитель получает роль, очередь и условия передачи. Проверить, что оба чата доступны и могут получить сообщения; первая успешная передача и возврат результата подтвердят механизм. Не объявлять автоматическое продолжение работающим до такой проверки.

Пример поручения **исполнителю** — пользователь заполняет данные в скобках:

> Работай по `docs/agents/two-chat/README.md` как исполнитель. Выбирай готовые независимые задачи frontend, API и backend интеграции из Linear [или: список задач]. Делегируй до трёх задач параллельно отдельным субагентам, каждой назначь свою ветку и worktree внутри `doccheck/.worktrees/`. База PR: `main`. ML/OCR и внутренняя обработка — за Семёном. Разрешаю отправлять запросы на ревью в мой чат [ссылка или ID чата ревьюера], при необходимости вызывать Codex Code Review через `@codex review` в PR и самостоятельно сливать свои PR в `main` после двух независимых ревью и проверок по этому режиму. Передавай готовые PR на ревью и продолжай независимую очередь; сливай последовательно. Done и деплой остаются за мной.

Пример поручения **ревьюеру**:

> Работай по `docs/agents/two-chat/README.md` и `docs/agents/reviewer.md` как независимый ревьюер. Для каждого PR запускай отдельного субагента с независимым контекстом; веди до трёх проверок параллельно по актуальным задачам Linear и точным base/head. Разрешаю публиковать результаты ревью в соответствующих PR и отправлять результат в мой чат исполнителя [ссылка или ID]. Код и статусы не меняй, PR не мёрджи.

Приведённый шаблон исполнителя разрешает автослияние только его собственных PR в `main` при выполнении условий ниже. Без такого поручения слияние остаётся человеку. Шаблоны не дают разрешения читать закрытые материалы, создавать чаты или выполнять деплой. Если прямое сообщение между чатами недоступно или не разрешено, пользователь передаёт запрос и результат вручную; ссылки на PR и вердикты остаются в GitHub. Обычный комментарий в GitHub или Linear сам по себе не запускает второй чат.

## Очередь и выбор следующей задачи

1. Перед выбором перечитать задачу в Linear, её описание, критерии, владельца и зависимости; проверить связанные ветки, PR и текущий `main` в GitHub, чтобы не дублировать работу. Не считать `In Review` или статус Linear доказательством, что зависимость уже доступна. Сверять фактическую версию, отзывы, CI и потребность в решении владельца. Не присваивать себе задачи Семёна и не предполагать готовность ML.
2. Выбрать до трёх готовых независимых задач и назначить по одной свободному субагенту. Проверить Linear и GitHub: локальный журнал не является блокировкой между устройствами. Если другая работа над задачей уже ведётся или владение неясно, не назначать дубль, а согласовать границы. Пока предыдущий PR не принят в целевую базу, не строить зависимую задачу на его непроверенном поведении. При отсутствии подходящих задач сообщить ожидаемые ревью или зависимости.
3. Для каждой задачи основной чат создаёт отдельную ветку и worktree внутри `doccheck/.worktrees/` по разделу выше; субагенту передаются её границы. Ревьюер не переключает ветку и не изменяет рабочую копию исполнителя; для чтения использует GitHub или фиксированные Git-объекты.
4. Не использовать `reset`, `clean`, `stash`, переключение ветки или удаление worktree поверх чужих либо незакоммиченных изменений. Если пользователь запретил worktree или они недоступны, выполнять изменения в общей копии последовательно, не отменяя параллельное чтение и независимое ревью.

Для восстановления исполнитель может вести локальный журнал в игнорируемом `data/two-chat/` основной копии: NRT-ID, ветка, путь worktree, PR, base/head, ожидаемый или полученный отзыв, ссылки на замечания и состояние текущей работы. Проверить, что путь игнорируется Git; не записывать в него секреты, документы, OCR-текст или эталон. Исполнитель — единственный редактор журнала. Это подсказка для восстановления, не замена Linear и GitHub; после перерыва сверить все записи с источниками и не стирать состояние другого запуска.

## Передача на ревью и продолжение

1. Исполнитель проводит применимые проверки, сохраняет изменения, открывает PR и оформляет его по `CONTRIBUTING.md`: актуальные цель, область и критерии из Linear с датой чтения, проверки, ограничения и отчёт `docs/agent-runs/`. Передаёт задачу в `In Review` с меткой `review`.
2. Исполнитель отправляет в разрешённый чат ревьюера ссылку на PR, NRT-ID, точные base и head SHA, ссылку на задачу, команды проверок и известные ограничения. Отдельно проверяет запуск Codex Code Review; если бот не запустился, при разрешении пользователя один раз вызывает `@codex review` в PR, зафиксировав base/head и время запроса. Перед повтором сначала проверяет существующий запрос и результат. Затем исполнитель фиксирует оба ожидаемых ревью в журнале и сразу переходит к следующей независимой задаче, не ожидая результата.
3. Ревьюер назначает каждый PR отдельному субагенту по [инструкции независимого ревьюера](../reviewer.md), без истории рассуждений автора, и ведёт до трёх проверок параллельно. По возможности субагент читает актуальную задачу Linear напрямую; иначе использует переданный контекст и отмечает ограничение. Ревьюер и его субагенты не пишут проверяемый код, не меняют рабочие копии и статусы и не сливают PR. Повторную проверку исправлений можно поставить впереди новых PR.
4. Ревьюер публикует разрешённый отзыв с `pass`, `changes_requested` или `blocked`, ссылкой на PR, NRT-ID, base/head, проверками, замечаниями и непроверенными пунктами. Отдельно отправляет эту ссылку и вердикт в разрешённый чат исполнителя. При недоступности отправки фиксирует результат в PR и сообщает пользователю; не утверждает, что исполнитель получил уведомление.
5. Исполнитель проверяет поступившие результаты на безопасных границах работы и между задачами. Сообщение не обязано прерывать текущую команду. Перед возвратом он сохраняет состояние текущей задачи, сверяет в GitHub действующие base/head, CI и все замечания обоих ревью, затем открывает worktree предыдущей задачи. При `changes_requested` проверяет замечания, исправляет подтверждённые проблемы, повторяет затронутые проверки, публикует новый head и отправляет его на оба повторных ревью; при спорном замечании объясняет основание и передаёт вопрос владельцу. При `blocked` устраняет доступный блокер или фиксирует его и продолжает независимую работу. При `pass` от второго чата и завершённом ревью бота проверяет условия автослияния ниже.
6. Оба отзыва относятся к проверенным версиям. При изменении head или base получить оба ревью для актуальной пары и повторить необходимые проверки; старый вердикт нельзя переносить на новую версию. Если уведомление продублировано, повторно сверить PR и не выполнять уже обработанные действия.

Если за время работы другой PR уже изменил `main`, основной чат исполнителя приостанавливает слияние затронутого PR, передаёт автору задачу обновить его ветку на актуальную базу и разрешить конфликты. После rebase или другого согласованного обновления проверить итоговый diff, повторить применимые проверки и оба ревью для новой пары base/head. Только после этого можно вернуть PR в очередь слияния. Публикуя переписанную собственную ветку, проверять права и заранее считанный удалённый head; при необходимости использовать явный `--force-with-lease=refs/heads/<ветка>:<проверенный-SHA>`. При несовпадении остановить push и выяснить, кто изменил ветку; обычный `--force` и обход защиты веток не применять.

## Автоматическое слияние в main

Если пользователь разрешил автослияние, исполнитель последовательно проверяет каждый свой PR:

1. **Два независимых отзыва.** Отдельный чат, не писавший изменения, дал `pass` для текущих base/head и описал выполненные проверки и ограничения. Codex Code Review в GitHub завершён для текущего полного head SHA, его результат принадлежит боту, а замечания разобраны. Подтверждением может служить актуальная сводка бота с `code_review.status: completed` и соответствующим `commit_sha`; проверить также `has_unresolved_findings` и сами замечания. Реакция, отсутствие комментариев, один успешный CI или отзыв только одного ревьюера не доказывают выполнение обоих условий. Если сводка не указывает базу, сопоставить базу на момент запуска и завершения; при неизвестной или изменившейся базе запросить новый отзыв и фиксировать пару и время запроса. Если ревью не запускается или вердикт неясен, PR остаётся открытым, а исполнитель продолжает независимую очередь.
2. **Замечания и CI.** Все существенные замечания обоих ревью исправлены и повторно проверены либо обоснованно разрешены; спорные и заблокированные вопросы не считаются проходом. Необходимые применимые CI и локальные проверки успешно завершены, нет непрочитанных ошибок и незавершённых обязательных проверок. Проверить, что CI относится к совместному результату текущих base/head, а не только к старой версии ветки; если это нельзя установить, не объявлять проверку успешной.
3. **Последняя сверка.** PR открыт, направлен в `main`, относится к задаче исполнителя и допускает слияние по правилам GitHub. Непосредственно перед merge ещё раз сверить текущие base/head, результаты ревью, CI и замечания. При изменении версии вернуться к ревью и проверкам. Передать GitHub ожидаемый проверенный head SHA; не обходить защиту ветки и не применять force-push вместо обычного merge PR. Свои merge в `main` выполнять последовательно.
4. **После merge.** Проверить в GitHub факт слияния и итоговый коммит, затем сообщить пользователю ссылку на PR, результаты двух ревью и проверок и оставшиеся ограничения. Для обычного merge-коммита сверить его родителей с проверенными base/head и CI с итоговым деревом; при squash или rebase проверить соответствующую историю и содержимое. Если фактическую пару установить нельзя, отметить её как непроверенную. Оставить задачу в `In Review` для человеческой приёмки; `Done` не выставлять автоматически. Если база успела измениться между последней сверкой и merge, зафиксировать это и сообщить пользователю: проверка ожидаемого head в GitHub сама по себе не блокирует изменение base. Не выдавать ранее проверенную пару за фактически объединённую; проверить фактическую интеграцию, её CI и необходимость независимого повторного ревью. Обнаруженную проблему исправлять отдельным согласованным изменением, а не скрывать расхождение версий.

Без явного разрешения на автослияние, при недоступном отзыве, проверке или GitHub, неоднозначном результате, новом base/head, конфликте или блокирующем замечании PR не сливается. Это не останавливает работу над другими независимыми задачами. Порядок применяется к PR исполнителя в этом режиме; ночной регламент, чужие PR, деплой и человеческая приёмка остаются без изменений.

Если чат исполнителя уже завершил ход, его возобновление зависит от доступного механизма доставки и разрешений: проверенный прямой запрос может продолжить чат, иначе пользователь передаёт результат и возобновляет его вручную. Если исполнитель активен, он обрабатывает результат в ближайшей безопасной точке. При сбое связи или недоступности Linear/GitHub не угадывать вердикт и не сливать PR; продолжать только работу, независимую от недоступных сведений. Плановое продолжение или автоматизация не создаются без отдельного запроса пользователя.
