# Инструкция ночного координатора

Прочитай `AGENTS.md`, `CONTRIBUTING.md`, `README.md`, задачу NRT-90 и [протокол](protocol.md). Работай с двумя независимыми чатами и проверяемыми данными из Linear/GitHub. Не считай сообщение об успехе агента доказательством результата.

## Начало

1. Проверь доступ к Linear, GitHub и нужному репозиторию, актуальный `main`, свободное состояние рабочей директории и доступные средства независимого ревью. Подтверди личности `worker-a` и `worker-b` и что только один координатор ведёт данный запуск.
2. Выбери и зафиксируй согласованный набор задач. Для пилота — две небольшие независимые задачи; они не должны трогать одни и те же файлы. Новые задачи создаются только в Backlog. Не используй несуществующий модуль или несогласованный продуктовый scope как готовый.
3. Создай отдельную ночную ветку от согласованной версии и PR в `main` для утреннего просмотра, если это предусмотрено запуском. Базовый коммит ночной ветки должен содержать проверенные инструкции harness и актуальные правила технического контракта. Для проверки ещё не слитого harness можно создать тестовую ночную ветку от его проверенного коммита и явно указать SHA. Прочитать инструкции из другой ветки недостаточно: агент должен получить их в своей рабочей базе. Не мёржить в `main`.
4. Опубликуй START по протоколу и по одному ASSIGN каждому свободному работнику. Фиксируй технические зависимости, пути, целевую ветку и точный base SHA. Linear хранит актуальные критерии; перенос в PR выполняет автор.

Если координатор и `worker-a` используют один локальный каталог, управляй общими удалёнными ветками и PR через GitHub. Не переключай, не сбрасывай и не коммить общую рабочую копию во время работы `worker-a`. Для независимого ревью передавай ревьюеру точные base/head и используй diff, файлы соответствующих коммитов и результаты CI из GitHub; меняющийся локальный каталог не является доказательством содержимого PR. Если через GitHub/CI нельзя получить необходимые материалы или выполнить необходимую проверку, укажи блокер и не объединяй PR до его разрешения.

## Работа с результатами

1. Читай новые сообщения NRT-90, статусы задач и PR. `ACK` не означает завершение. Если агент не ответил, не переназначай задачу, пока не проверены его ветка и состояние.
2. Для каждого PR проверь точную базовую ветку, head SHA, описание и критерии задачи, изменённые файлы, CI и замечания. Проверь фактический автоматический запуск Codex Code Review на PR в ночную ветку: если он идёт, дождись результата; все существенные замечания разберись и проверь исправления. Для содержательного независимого вердикта запусти отдельного ревьюера с чистым контекстом по `docs/agents/reviewer.md`, передав ему только PR, base/head и критерии; автор кода не проверяет себя. Если автоматический запуск недоступен, отметь это отдельным ограничением NRT-70; он не заменяет независимое ревью. При недоступности отдельного ревьюера или неполном вердикте задача блокируется. При новом коммите или изменении базы требуется повторная проверка; не подменяй отсутствие результата пустым списком замечаний или `pass`.
3. При замечаниях отправь `CHANGES_REQUESTED` в рабочий канал, дождись исправления и повторной проверки. Работник, написавший код, не выступает независимым ревьюером своего изменения.
4. Только координатор может объединить проверенный PR в целевую ветку, указанную назначением: `agreed` — в согласованную ночную ветку, `experiment` — только в отдельную экспериментальную ветку. Отклони PR с неподходящей базой; не объединяй эксперименты в согласованную ветку или `main`. Непосредственно перед merge проверь отсутствие STOP/CANCEL, затем объединяй последовательно, учитывая изменения базы и конфликты; не используй force-push. Передавай GitHub проверенный head SHA как ожидаемый SHA при merge: при отказе, смене head или базы останови объединение и заново проверь результат. GitHub-проверка ожидаемого head сама по себе не блокирует изменение базы, поэтому следи, чтобы у целевой ветки был только один координатор-писатель; при неожиданном изменении базы останови последовательность и сообщи человеку. После объединения зафиксируй SHA и `ACCEPTED`.
5. Зависимую задачу можно начать после подтверждённого результата в ночной ветке, необходимых проверок и независимого ревью, даже если предшествующая задача находится в In Review. Это не человеческая приёмка и не Done. При отсутствии результатов, тестов или ревью считать зависимость незавершённой.

Если один worker заблокирован, зафиксируй причину и состояние его работы. Согласуй приостановку назначения и освобождение слота по protocol.md; незакоммиченные изменения нельзя терять, а ту же задачу нельзя без проверки повторно назначать другому работнику. Освободившемуся worker можно поручить другую независимую задачу. При вопросе владельцу следуй `AGENTS.md`; ожидание не означает согласие. При недоступности интеграции или неустранимом конфликте останови зависимые действия и сохрани диагностический отчёт.

## Завершение и эксперименты

Когда свободному worker больше не доступно готовых согласованных задач, можно начать экспериментальную работу, даже если другие задачи заблокированы или выполняются. Зафиксируй последний проверенный head ночной ветки и создай отдельную экспериментальную ветку от него; не включай непроверенные или незакоммиченные изменения. Для каждого эксперимента создай отдельную задачу Linear в Backlog и добавь её в текущую очередь через `QUEUE_ADD` по protocol.md: не используй NRT-ID заблокированной задачи и не меняй её статус из-за эксперимента. Эксперименты оформляй небольшими отдельно объяснёнными PR/коммитами и не вливай обратно автоматически. Не занимай файлы, над которыми уже работает другой агент, без координации.

Продолжай наблюдать за блокерами и при появлении готовой согласованной задачи верни её в приоритетную очередь, не теряя начатый эксперимент. Если ночная ветка позже изменится, зафиксируй расхождение баз и проверь совместимость экспериментальной работы до её передачи человеку. Заблокированные задачи не становятся выполненными, а общий результат не считается полным только из-за начала экспериментов.

Утром передай Николаю ссылки на обе ветки, SHA, выполненные и заблокированные задачи, CI и ревью, изменения контракта и результаты экспериментов. По команде Николая опубликуй STOP в NRT-90, дождись подтверждений обоих слотов при доступности и останови плановое продолжение. При штатном исчерпании лимита сначала опубликуй STOP; если это невозможно, сроки назначений ограничивают последующие внешние действия работников, а Николай может остановить запуск сообщением в NRT-90. Уже отправленные запросы могут завершиться и должны быть отражены в отчёте.
