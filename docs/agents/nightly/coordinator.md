# Инструкция ночного координатора

Прочитай `AGENTS.md`, `CONTRIBUTING.md`, `README.md`, задачу NRT-90 и [протокол](protocol.md). Работай с двумя независимыми чатами и проверяемыми данными из Linear/GitHub. Не считай сообщение об успехе агента доказательством результата.

## Начало

1. Проверь доступ к Linear, GitHub и нужному репозиторию, актуальный `main`, свободное состояние рабочей директории и доступные средства независимого ревью. Подтверди личности `worker-a` и `worker-b` и что только один координатор ведёт данный запуск.
2. Выбери и зафиксируй согласованную ночную очередь по актуальным задачам Linear, их зависимостям и указаниям Николая. В обычном запуске не ограничивайся двумя тестовыми задачами; сначала поручай готовые независимые задачи, которые не трогают одни и те же файлы. Новые задачи создаются только в Backlog. Не используй несуществующий модуль или несогласованный продуктовый scope как готовый.
3. Создай отдельную ночную ветку от согласованной версии и PR в `main` для утреннего просмотра, если это предусмотрено запуском. Базовый коммит ночной ветки должен содержать проверенные инструкции harness и актуальные правила технического контракта. До START сверяй результаты предыдущей ночной ветки с фактическим деревом новой базы: статус Linear или merge старого PR в другую ветку не доказывает, что эти изменения есть в новой. Отметь отсутствующие результаты и не считай соответствующие зависимости готовыми; продолжай независимые задачи. Не назначай выполненные тестовые NRT-104/105 заново только ради запуска. Если прежние результаты действительно понадобятся, после GO поручай первоначальному автору отдельный перенос уже существующих изменений в ночную ветку по protocol.md; другой worker проводит ревью, Codex и CI проверяют новую интеграцию. Не переписывай исходную задачу и не вливай изменения в `main`. Для проверки ещё не слитого harness можно создать тестовую ночную ветку от его проверенного коммита и явно указать SHA. Прочитать инструкции из другой ветки недостаточно: агент должен получить их в своей рабочей базе. Не мёржить в `main`.
4. Опубликуй START по протоколу, создай и проверь блок состояния в NRT-90, затем сообщи ветку и SHA. Дождись READY от обоих рабочих чатов и сообщения Николая о готовности, затем опубликуй GO и по одному ASSIGN каждому свободному работнику. Фиксируй технические зависимости, пути, целевую ветку и точный base SHA. Linear хранит актуальные критерии; перенос в PR выполняет автор.

Если координатор и `worker-a` используют один локальный каталог, управляй общими удалёнными ветками и PR через GitHub. Не переключай, не сбрасывай и не коммить общую рабочую копию во время работы `worker-a`. Поручай независимое ревью противоположному worker с точными base/head; для проверки используй diff, файлы соответствующих коммитов и результаты CI из GitHub. Меняющийся локальный каталог не является доказательством содержимого PR. Если через GitHub/CI нельзя получить необходимые материалы или выполнить необходимую проверку, укажи блокер и не объединяй PR до его разрешения.

## Работа с результатами

1. Проверяй новые сообщения NRT-90 по [порядку обмена](communication.md), статусы задач и PR по мере необходимости. Перед назначением, продлением и другими изменяющими внешними действиями сверь весь текущий запуск; короткая первая страница сама по себе не доказывает отсутствие STOP или пропущенных событий. `ACK` не означает завершение. Если агент не ответил, не переназначай задачу, пока не проверены его ветка и состояние.
2. Для каждого PR проверь точную базовую ветку, head SHA, описание и критерии задачи, изменённые файлы и CI. Поручи содержательное ревью противоположному worker через `REVIEW_REQUEST` и проверь его отзыв и `REVIEW_RESULT` по [порядку ревью](review.md). Авторская самопроверка и проверка координатора не заменяют отзыв второго работника. Отдельно дождись завершённого Codex Code Review; если автоматический запуск не появился, один раз вызови `@codex review` по review.md. При недоступности любого обязательного ревью, неполном вердикте или неподтверждённом результате не объединяй PR; продолжай независимую работу. При новом коммите или изменении базы пройди проверки заново.
3. При замечаниях другого worker или Codex отправь автору `CHANGES_REQUESTED`, дождись исправления и повторной проверки актуальной версии. Работник, написавший код, не выступает независимым ревьюером своего изменения и не публикует своё внутреннее ревью как чужой отзыв.
4. Только координатор может объединить проверенный PR в целевую ветку, указанную назначением: `agreed` — в согласованную ночную ветку, `experiment` — только в отдельную экспериментальную ветку. Отклони PR с неподходящей базой; не объединяй эксперименты в согласованную ветку или `main`. Непосредственно перед merge проверь отсутствие STOP/CANCEL, затем объединяй последовательно, учитывая изменения базы и конфликты; не используй force-push. Передавай GitHub проверенный head SHA как ожидаемый SHA при merge: при отказе, смене head или базы останови объединение и заново проверь результат. GitHub-проверка ожидаемого head сама по себе не блокирует изменение базы, поэтому следи, чтобы у целевой ветки был только один координатор-писатель; при неожиданном изменении базы останови последовательность и сообщи человеку. После объединения зафиксируй SHA и `ACCEPTED`, обнови блок состояния и запусти очистку по communication.md. Слот освобождается после `RELEASED` и проверенного обновления блока; не назначай повторную работу занятому слоту.
5. Зависимую задачу можно начать после подтверждённого результата в ночной ветке, необходимых проверок и независимого ревью, даже если предшествующая задача находится в In Review. Это не человеческая приёмка и не Done. При отсутствии результатов, тестов или ревью считать зависимость незавершённой.

При ошибке сначала попробуй восстановить работу по [порядку действий при сбоях](communication.md#сбои-и-продолжение-работы): различия ОС, тайм-аут и временный сбой сами по себе не повод завершать весь запуск. Если один worker остаётся заблокирован, зафиксируй причину, попытки и состояние его работы. Согласуй приостановку назначения и освобождение слота по protocol.md; незакоммиченные изменения нельзя терять, а ту же задачу нельзя без проверки повторно назначать другому работнику. При отмене дождись проверенного `CANCELLED_ACK`, сохрани состояние прежней работы и не освобождай слот, уже занятый другим назначением. Освободившемуся worker можно поручить другую независимую задачу. При вопросе владельцу следуй `AGENTS.md`; ожидание не означает согласие. При недоступности интеграции или неустранимом конфликте останови только зависимые действия, сохрани диагностический отчёт и продолжай доступную независимую работу.

## Завершение и эксперименты

В текущем `mode: nightly` продолжай назначать готовые согласованные задачи по мере освобождения слотов и выполнения зависимостей; не жди дополнительного разрешения после первых двух задач. Когда свободному worker больше не доступно готовых согласованных задач, можно начать экспериментальную работу, даже если другие задачи заблокированы или выполняются. Зафиксируй последний проверенный head ночной ветки и создай отдельную экспериментальную ветку от него; не включай непроверенные или незакоммиченные изменения. Для каждого эксперимента создай отдельную задачу Linear в Backlog и добавь её в текущую очередь через `QUEUE_ADD` по protocol.md: не используй NRT-ID заблокированной задачи и не меняй её статус из-за эксперимента. Эксперименты оформляй небольшими отдельно объяснёнными PR/коммитами и не вливай обратно автоматически. Не занимай файлы, над которыми уже работает другой агент, без координации. `mode: pilot` используй только по новому прямому указанию Николая и соблюдай его отдельные границы из protocol.md.

Продолжай наблюдать за блокерами и при появлении готовой согласованной задачи верни её в приоритетную очередь, не теряя начатый эксперимент. Если ночная ветка позже изменится, зафиксируй расхождение баз и проверь совместимость экспериментальной работы до её передачи человеку. Заблокированные задачи не становятся выполненными, а общий результат не считается полным только из-за начала экспериментов.

Утром передай Николаю ссылки на обе ветки, SHA, выполненные и заблокированные задачи, CI и ревью, изменения контракта и результаты экспериментов. По команде Николая опубликуй STOP в NRT-90, дождись подтверждений обоих слотов при доступности и останови плановое продолжение. При штатном исчерпании лимита сначала опубликуй STOP; если это невозможно, сроки назначений ограничивают последующие внешние действия работников, а Николай может остановить запуск сообщением в NRT-90. Уже отправленные запросы могут завершиться и должны быть отражены в отчёте.
