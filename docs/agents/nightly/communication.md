# Обмен сообщениями ночного запуска

Linear — источник текущего состояния и событий запуска; локальное состояние помогает не читать повторно одну и ту же историю, но не заменяет Linear. GitHub хранит ветки, PR и коммиты. Каждый из трёх чатов имеет свою роль и своё локальное состояние; чаты на разных устройствах не разделяют память.

## Состояние в начале NRT-90

В начале описания NRT-90 координатор создаёт отдельный блок между обычными заголовками `## Ночное состояние — начало` и `## Ночное состояние — конец`. Не заменять цель, критерии или другие части задачи. При подготовке запуска, во время него и при переходе между запусками координатор — единственный редактор **всего описания NRT-90**; работники и люди передают команды и вопросы комментариями или в чат, а не редактируют описание одновременно с ним. Это рабочая договорённость, не техническая блокировка Linear.

Для чтения использовать `linear_get_issue` с NRT-90 и полями `description`, `updatedAt`. При первом создании, если обоих заголовков нет, добавить блок в начало через `linear_save_issue` с `patch: prepend`; для последующих обновлений передать `patch: replace` с точным прежним и новым текстом блока. Если заголовки неоднозначны или найден только один, не пытаться исправить описание вслепую. Перечитать и проверить результат вместе с неизменённой остальной частью задачи. Чтение, запись и повторное чтение не образуют атомарную операцию и не гарантируют обнаружение чужой правки, сделанной одновременно. При известном или подозреваемом конкурирующем редактировании, конфликте или неожиданном результате остановить зависимые действия и восстановить состояние с участниками; не объявлять простую повторную проверку защитой от перезаписи.

В блоке указать версию протокола, `run_id`, возрастающую `revision`, режим и состояние запуска, координатора, ночную и экспериментальную ветки, GO/STOP, занятость обоих слотов, активные назначения и незавершённые блокеры. Отдельно перечислять все неразобранные назначения: активные на момент STOP, приостановленные, включая эксперименты, и отменённые с сохраняемой работой. Указать прежний `run_id`, `assignment_id`, задачу, владельца, область файлов, ветку, PR, место сохранения локальных изменений и неопределённые действия, даже когда блокера нет и слот свободен. До `CANCELLED_ACK` и проверки состояния отмена не освобождает занятый слот. Координатор обновляет блок по мере обработки назначения, продления, приостановки, отмены, завершения и остановки. До исполнения ASSIGN работник должен увидеть его и в комментарии, и в состоянии; при расхождении дождаться согласованного состояния координатора, а не угадывать. Активное назначение содержит область файлов и действующий срок; его подробности можно взять из ещё не удалённого ASSIGN и актуального RENEW.

По завершённому назначению достаточно одной строки с `run_id`, `assignment_id`, NRT-ID, `worker`, видом работы, ссылками на PR и точный коммит объединения, результатом, `result_revision` и признаком `cleanup: waiting | ready`. `result_revision` — номер `revision`, в которой впервые зафиксирован именно этот итог; он не меняется при обновлении других заданий. При изменении самого итога ему присваивается новая версия. Коммит можно указать прямой ссылкой GitHub, содержащей полный SHA. Полные проверки и ограничения остаются в PR и отчёте задачи. Эти компактные строки составляют реестр завершённых назначений и переносятся между запусками: даже после видимой очистки старый комментарий может появиться с задержкой. In Review не означает человеческую приёмку.

Пример сокращённого блока, значения условные:

```text
## Ночное состояние — начало
run_id: n90-20261112-1953
revision: 4
run: active
worker-a: свободен
worker-b: b1, NRT-<номер>, в работе
завершено: a1, NRT-<номер>, PR <ссылка>, merge <ссылка на коммит>, result_revision: 3, cleanup: ready
## Ночное состояние — конец
```

При каждой проверке сначала получать актуальный блок через `get_issue` NRT-90. Чаты учитывают только проверенную версию своего запуска и затем читают ещё не обработанные комментарии, включая команды STOP и события другого слота. Не считать отсутствие нового текста в summary доказательством, что новых комментариев нет: их пишет не только координатор. Если блок отсутствует, повреждён, версии противоречат друг другу или обновление невозможно подтвердить, восстановить состояние по Linear и GitHub; зависимые действия и очистку до восстановления не выполнять.

## Очистка завершённой задачи

1. После фактических CI, независимого ревью и объединения PR в назначенную ночную или экспериментальную ветку координатор записывает `ACCEPTED` и фиксирует итог назначения в блоке состояния с `cleanup: waiting`. Проверяет, что в задаче и PR остаются ссылка, итог, результаты проверок и ограничения. Не считать `RESULT`, `BLOCKED`, `PAUSE` или один статус Linear завершением.
2. Работник читает опубликованное состояние и подтверждённый результат, завершает действия и сохраняет свои локальные изменения. Когда назначение больше не выполняется и нет неопределённых запросов, публикует `RELEASED` с `run_id`, `assignment_id`, `worker` и увиденной `result_revision`. Иначе сообщает блокер; слот остаётся занят. Если работник временно недоступен, не принимать молчание за подтверждение и не удалять его сообщения.
3. Координатор проверяет автора `RELEASED` по GO, слот, назначение и совпадение `result_revision` с итогом этого назначения. Изменение общей `revision` из-за другого слота не аннулирует подтверждение неизменившегося итога. Координатор обновляет блок: указывает освобождённый слот и `cleanup: ready` для этого назначения, увеличивает `revision` и перечитывает успешно сохранённое состояние. Только после этого запись завершённого назначения считается основой для очистки; другие активные назначения и их события остаются без изменений.
4. Координатор удаляет созданные своей ролью, а соответствующий работник — созданные своей ролью технические комментарии этого назначения через `linear_delete_comment`. События координатора: `ASSIGN`, `RENEW`, `ACCEPTED`, `CHANGES_REQUESTED`, `PAUSE`, `CANCEL`, `RESUME`, `QUEUE_ADD`; события работника: `ACK`, `RESULT`, `BLOCKED`, `PAUSED_ACK`, `CANCELLED_ACK`, `RELEASED`. Само по себе `CANCELLED_ACK` не означает принятия задачи и не даёт `cleanup: ready`. Каждый чат проверяет такой остаток при получении `cleanup: ready` и после восстановления; не ждать отдельной просьбы человека. Если уже есть следующее назначение, попытку очистки выполнить между его шагами. Перед каждым удалением заново сверять опубликованный блок, `run_id`, `assignment_id`, тип события и автора с текущей учётной записью Linear (`get_user` с `me`); проверить отсутствие STOP и актуальный список комментариев. Для `QUEUE_ADD` без `assignment_id` допустима очистка только по точному `run_id` и NRT-ID завершённого эксперимента, когда других активных назначений этой задачи нет. Координатор и worker-a могут делить учётную запись: проверка автора не заменяет проверку роли и типа события.
5. Удалять только однозначные протокольные сообщения, относящиеся к этому назначению; не удалять START, GO, STOP, STOPPED, сообщения людей, события других или ещё выполняющихся назначений. Не удалять комментарий с вложением, цитатой в описании или ответами в треде: сначала сохранить содержимое и разобраться с владельцем, иначе отметить невозможность очистки. При полной сверке перед удалением собрать на всех страницах `parentId` **всех** комментариев, включая обычные сообщения людей, и проверить у удаляемого комментария `attachments` и `quotedText`. Можно вычислить и вывести только необходимые признаки и автора, не выводя тела посторонних сообщений. Пример фильтра ниже не сохраняет эти признаки и сам по себе недостаточен для решения об удалении. Если полноту страниц или нужные признаки проверить нельзя, не удалять. При недостатке прав или неизвестном авторе оставить комментарий и сообщить координатору; при неопределённом результате удаления не считать его выполненным. Ошибка очистки не делает задачу невыполненной и сама по себе не блокирует независимую очередь.

После очистки отсутствие старого события допустимо только для назначения с проверенным `cleanup: ready` в актуальной версии состояния. При изменении `revision` чаты перечитывают блок, обновляют локальный чекпоинт и при необходимости заново проходят страницы комментариев; незнакомую пропажу или изменение события активного назначения считать неоднозначностью. Старые события назначения с `cleanup: ready`, которые ещё не удалось удалить или которые отобразились с задержкой, не оживляют его и не дают повторного назначения; принадлежащий роли чат предпринимает очистку при следующем обнаружении. Не очищать прежние запуски `v1` этим порядком без отдельного подтверждённого переноса их итогов и остановки всех участников.

### Отложенная очистка после STOP

STOP немедленно прекращает очистку текущего запуска. До неё строки `cleanup: waiting` и `cleanup: ready` сохраняются в его состоянии; отсутствие работника или ошибка удаления не превращаются в успешную очистку. Перед новым START координатор проверяет остановку прежних работников и сохранность их работы и подготавливает перенос реестра завершённых назначений, в том числе незавершённой очистки, с прежними `run_id`, `assignment_id`, NRT-ID, `worker`, `work_kind`, `result_revision`, PR и коммитом. Также перенести **все** неразобранные назначения прежнего запуска, включая активные на момент STOP, приостановленные и отменённые с сохраняемой работой. Для них сохранить `run_id`, `assignment_id`, задачу, worker, область файлов, ветку, PR, место локальных изменений и неопределённые запросы; старый STOP не делает их выполненными.

Перед заменой блока полностью перечитать страницы сообщений предыдущего запуска с его `run_id`, включая ASSIGN/ACK/RESULT/BLOCKED и STOPPED, и сверить их с прежним блоком, GitHub и состоянием устройств. При недостающих или противоречивых данных зафиксировать неразобранную работу и не занимать её слот или область файлов до выяснения. Старый блок до START не менять. После подтверждённого START заменить его новым блоком с подготовленными сведениями и проверить результат до приглашения работников. Если START, перенос или проверка не подтверждены, не назначать задачи и сохранять информацию для восстановления. В новом запуске прежний STOP не разрешает возобновить старое назначение: координатор отдельно проверяет сохранённую ветку, PR и изменения и согласует новое назначение, не создавая повторный PR.

Когда новый запуск активен и его STOP отсутствует, каждый чат может удалить **свои** оставшиеся технические комментарии прежнего запуска с `cleanup: ready`: дополнительно сверить прежний STOP, безопасную остановку слота, перенесённый итог и точные идентификаторы. STOP прежнего запуска не запрещает такую доочистку; STOP нового её прекращает. Если автор сообщения недоступен или права изменились, сохранить запись в отложенной очистке и передать ограничение Николаю, продолжая независимые задачи.

Запись `cleanup: waiting` нельзя превратить в `ready` только потому, что прежний запуск остановлен. Для её восстановления первоначальный работник под той же подтверждённой учётной записью в новом запуске проверяет прежний STOP и STOPPED, перенесённый итог и `result_revision`, PR и коммит в GitHub, сохранённое локальное состояние и отсутствие неопределённых запросов. Если всё подтверждено без переключения или перезаписи текущей работы, он публикует верхнеуровневый `RELEASE_OLD` с новым `run_id`, прежним `previous_run_id`, прежним `assignment_id`, своим `worker` и прежним `result_revision`. Это подтверждение очистки, а не возобновление старого назначения.

Координатор проверяет автора по учётным записям слота в GO обоих запусков, прежний STOP/STOPPED и итог, затем меняет перенесённую запись на `cleanup: ready` и увеличивает `revision`. После подтверждения состояния работник может удалить и своё `RELEASE_OLD`, только если совпадают прежний `previous_run_id`, `assignment_id`, `worker`, `result_revision` и автор. Это относится и к `RELEASE_OLD`, опубликованному в промежуточном запуске до ещё одной остановки. Если старый работник, его состояние или исход действий недоступны, сохранить `waiting` и передать вопрос Николаю; не считать задачу или слот безопасными по догадке.

Даже после проверки удаления сохранить компактную запись в реестре: один полный просмотр не доказывает, что задержанное сообщение не появится позже. При следующем обнаружении подходящего комментария сверить реестр и повторить очистку по тем же правилам. Если исход удаления неизвестен или ещё остались сообщения, передать это как ограничение; работа над независимыми задачами продолжается. Сводный итог по задаче и PR должен оставаться доступен в Linear и GitHub.

## Сбои и продолжение работы

Не завершать весь запуск из-за первой ошибки, отличия окружения или блокера одной задачи. Сначала выяснить, что конкретно не работает, и попробовать допустимое решение; зафиксировать блокером только действия, которые действительно зависят от нерешённой проблемы. Продолжать остальную согласованную работу. Если свободному работнику нет готовых согласованных задач, в обычном ночном режиме действовать по правилам экспериментальной ветки; границы контролируемого пилота сохраняются.

- **Другая ОС или оболочка.** Определить фактическую ОС, рабочий каталог и доступные инструменты, затем использовать эквивалентные команды для этого устройства. Например, пути Windows сами по себе не являются основанием остановить работу на Mac. Проверять версии и выполнять установки или подготовку окружения только допустимым для проекта способом; не менять чужую копию и не выдавать непроверенное окружение за рабочее.
- **Временная ошибка чтения или связи.** Разобрать сообщение, проверить доступную авторизацию и подключение без раскрытия токенов; выполнить один-два обоснованных повтора либо использовать другой доступный авторизованный инструмент для того же источника. Учитывать ограничения сервиса и указанный срок ожидания, не запускать бесконечный цикл запросов. При восстановлении перечитать нужное состояние перед зависимым действием.
- **Зависшая локальная команда.** Проверить её сессию и вывод: тайм-аут ожидания не означает, что процесс остановился. По возможности продолжить наблюдение или безопасно прервать только собственный процесс; проверить состояние файлов и фактический результат перед повторным запуском. Не убивать чужие процессы и не удалять или перезаписывать чужую работу. Если результат неопределён, не запускать параллельный дубликат.
- **Неизвестный результат изменяющего запроса.** Если push, PR, комментарий, merge или другое внешнее действие могло завершиться после сбоя, оставить его `pending` и сначала проверить фактическое состояние в Linear/GitHub. Не повторять запрос и не переназначать занятую работу, пока его исход не установлен. Если доказательств нет, сохранять состояние и продолжать независимые действия.

Если после таких попыток конкретное действие остаётся недоступным, передать `BLOCKED` с причиной, уже предпринятыми попытками и сохранённым состоянием. Координатор согласует безопасное освобождение слота по protocol.md и по возможности выдаёт другую независимую задачу; отсутствие ответа не доказывает остановку работника. При временной недоступности Linear работник с ранее подтверждённым назначением может продолжать независимую локальную работу в его пределах, но не выполняет внешние действия, для которых нельзя заново проверить состояние и срок. Когда безопасных действий сейчас нет, сохранить состояние и ждать восстановления через следующее доступное продолжение, а не объявлять задачу успешной или прекращать весь запуск из-за одного сбоя.

Команду Николая `STOP` и системное ограничение выполнения соблюдать. Полный ночной запуск не закрывать из-за одного блокера; когда исчерпаны доступные согласованные задачи, учитывать возможность экспериментов и ограничение пилота. Продуктовые неизвестные, чужие изменения, отсутствие обязательного ревью и неподтверждённые результаты не обходить догадками ради продолжения.

## Когда проверять

- Во время активной работы не запускать фоновый или периодический опрос Linear и не проверять сообщения просто потому, что прошло время или закончился очередной внутренний шаг. Читать NRT-90, когда это нужно для следующего решения: при получении или возобновлении назначения, ожидании ответа, восстановлении после сбоя и перед изменяющими внешними действиями. Не повторять один и тот же запрос без нового основания. Если ответа ещё нет, продолжать независимую работу или завершить ход до планового продолжения; не создавать цикл постоянных запросов. Во время одного выполняющегося инструмента чат может не получать управление.
- До публикации событий, push, создания или изменения PR, смены статуса Linear, назначения или продления работы и merge сверять весь текущий запуск по правилам ниже, действующего координатора, конфликты, STOP, CANCEL и PAUSE/RESUME. Для действий по активному назначению работник также проверяет его срок; очистка уже завершённого назначения с `cleanup: ready` не требует действующего срока старого назначения. При недоступном канале или неоднозначном состоянии зависимое действие не выполняется. Чтение Linear или GitHub само по себе не является изменяющим действием и не требует отдельной предварительной сверки. Для STOP и STOPPED действует исключение ниже: недоступность полной сверки или чекпоинта не должна помешать попытке остановки.
- Для возвращения в тот же чат, если очередной ответ завершился, каждый чат создаёт одно плановое продолжение раз в минуту по [короткому шаблону](macos.md). Это отдельный запасной механизм, а не основание запускать ещё один опрос внутри активной работы. Не создавать ещё один независимый чат или дублирующее расписание. Продолжение не является уведомлением по событию Linear; наблюдаемое срабатывание и отсутствие конфликтующих запусков нужно проверить.
- Если новых событий или необходимого действия нет, ничего не публиковать в Linear и не писать длинный отчёт в чат. Приближение срока действующего назначения — отдельное основание для `RENEW`, даже когда новых сообщений нет: проверить локальные часы при доступном управлении, перед продлением сверить запуск и выполнить его по protocol.md. На новом событии выполнять следующий разрешённый шаг; сообщать человеку только о существенном изменении, блокере или результате. Не отправлять повторно ACK/RESULT/STOPPED только потому, что наступила минута.

`STOP`, опубликованный в Linear во время продолжительной локальной работы, будет замечен при следующей необходимой проверке или плановом продолжении, а не обязательно сразу. Уже запущенный запрос может завершиться.

## Быстрая проверка

1. Когда необходима быстрая проверка, запросить первую страницу из трёх последних комментариев NRT-90 по времени создания. Если уже известно, что нужна полная сверка, сразу запросить до 100 комментариев на первой странице и продолжить по курсору: это позволяет не делать отдельный запрос на три комментария. Использовать фактически доступную сортировку и курсор инструмента, проверить, что она выдаёт новые записи первыми. Поискать события `DOCCHECK-NIGHTLY/v2` текущего `run_id`, включая общие команды и события обоих слотов; одного поиска только по своему worker недостаточно для обнаружения конфликтов.
2. Сверить ID и время обновления комментариев с последней обработанной страницей. Если появились новые комментарии, догружать страницы до известной границы, чтобы обработать **все** увиденные события после неё, а не только три. Обрабатывать их в порядке создания, с дедупликацией по ID; одновременно опубликованные или противоречивые команды разбирать по идентификаторам и правилам протокола, не угадывать порядок при неоднозначности.
3. Если граница не найдена, состояние утеряно, появилась ошибка страницы, есть неоднозначность, чат перезапущен или восстановлен после долгого перерыва, выполнить полную сверку. Даже при найденной границе возможна задержка видимости комментария; читать **все страницы NRT-90** при каждом плановом продолжении, перед изменяющим внешним действием и после восстановления. Во время активной работы отдельного периодического интервала для полной сверки нет. При изменённом или пропавшем ранее обработанном событии учитывать подтверждённую очистку по состоянию выше; иные изменения считать неоднозначностью, восстановить состояние по Linear и при невозможности остановить зависимое действие.

Три комментария — размер страницы быстрой проверки, а не ограничение на число обрабатываемых событий. При полной сверке запрашивать страницы до 100 комментариев, если инструмент это поддерживает, и фильтровать их до вывода в контекст. Локальный чекпоинт не доказывает, что в Linear не появился старый или поздно отобразившийся комментарий. При каждой полной сверке учитывать события текущего запуска, START/READY/GO/STOP/STOPPED **всех** других запусков, в том числе `v1`, и сообщения завершённых и неразобранных назначений из блока состояния, независимо от даты: незавершённый другой запуск и параллельный координатор — блокер. При обнаружении другого активного запуска выполнить ещё один проход страниц с его `run_id`, не отсекая его назначения и ответы; изучить занятость слотов и путей. До выяснения не начинать конкурирующую работу.

Перед новым START проверить всю историю и остановку предыдущих запусков. Один STOP не доказывает, что работники успели его увидеть: перед повторным использованием каждого слота нужны его STOPPED с подтверждением отключения продолжения, отсутствие незавершённого запроса или выполняющейся старой работы и сохранённое состояние. Если этих подтверждений нет, слот остаётся занятым; можно использовать его только после подтверждённой человеком безопасной ручной остановки, проверки сохранности работы и отключения старого расписания на соответствующем устройстве. Не считать два STOPPED одного работника подтверждением другого. При неопределённости зафиксировать блокер, не начинать конкурирующую работу и не создавать новый START, который займёт этот слот.

Если во время прохода появились новые записи, перечитать начало и сверить найденные события; при нестабильной выдаче не выполнять зависимое внешнее действие. Даже полное чтение не делает проверку и последующее действие атомарными: STOP может появиться сразу после чтения или уже отправленного запроса. Повторить проверку непосредственно перед действием и зафиксировать фактический результат.

## Что хранить локально

Для каждой пары `run_id` и роли хранить небольшой чекпоинт в исключённом из Git `data/nightly-state/<run_id>/<role>.json`: версию протокола, идентификаторы и время обновления увиденных событий, границу страниц, состояние назначений, неподтверждённые действия и последнюю подтверждённую остановку. Для пути `run_id` должен соответствовать `^[A-Za-z0-9_-]+$`, а `role` — только `coordinator`, `worker-a` или `worker-b`. Координатор и worker-a на одной машине используют разные файлы, worker-b — файл в своей копии. Не хранить секреты, документы, OCR или реальные результаты. Перед использованием проверить, что путь действительно игнорируется Git.

Перед каждым изменяющим внешним действием — публикацией, push, PR, merge, сменой статуса, созданием расписания и т. п., кроме команд остановки ниже, — сначала атомарно сохранить в чекпоинт намерение `pending`: постоянный локальный ID операции, `run_id`, `assignment_id` при наличии, тип действия, его цель и существенные параметры. Например, для ASSIGN заранее выбрать и записать `assignment_id`, worker, задачу и границы; для PR и merge — целевую ветку и проверяемые версии. Только после сохранения отправить запрос. Удалить `pending` или пометить его подтверждённым после получения и фиксации фактического результата. Если сохранить намерение не удалось, зависимое внешнее действие не начинать. Для START заранее выбрать `run_id` и создать его чекпоинт; расписание запускать после подтверждения START.

Чекпоинт — не источник команд: при первом старте, потере или повреждении файла восстановить состояние из Linear, GitHub и локальной ветки. Обновлять обработанные события после их обработки. После сбоя сначала сверить каждое неподтверждённое действие с Linear и GitHub. Если запрос мог быть принят, но результата пока не видно или нельзя надёжно установить его исход, не повторять действие и не выбирать новый ID для того же назначения; отсутствие записи при одном полном чтении не доказывает, что запрос не был принят. Зафиксировать блокер и продолжить независимую работу. Если чекпоинт потерян и невозможно исключить незавершённый запрос, также не угадывать его исход. Не выполнять reset/stash и не удалять чужие изменения ради восстановления.

Остановка имеет приоритет: при команде STOP прекращать новые назначения и зависимые действия сразу, даже если другая операция ожидает подтверждения. Отправлять STOP и STOPPED и отключать своё плановое продолжение разрешено даже при недоступном чекпоинте. Доставку STOP и его фактический результат нужно проверить отдельно; при неопределённом результате допускается повторить тот же STOP или STOPPED для того же `run_id`, поскольку повторная остановка не возобновляет работу. Если доставку или отключение продолжения подтвердить не удалось, сообщить об этом Николаю. Не объявлять остальные действия отменёнными, если их результат ещё неизвестен.

## Как уменьшить вывод в контекст

Доступный Linear MCP умеет выдавать страницы комментариев с `limit`, `cursor` и сортировкой; серверного фильтра по `run_id`, типу события или тексту в этом интерфейсе нет. Если в среде чата доступен вызов MCP через код с обработкой результата до вывода, получать страницы там и выводить в контекст только новые события текущего запуска и данные, нужные для обнаружения других активных запусков: их ID, автора и компактное тело. START, команды остановки, конфликты и непонятные технические записи нельзя отбрасывать. При полной сверке страницы всё равно запрашиваются из Linear, просто старые обработанные события не выводятся в чат заново.

Если такого способа в конкретном чате нет, читать страницы обычным инструментом и не утверждать, что фильтрация до попадания в контекст работает. Длинные комментарии при этом всё ещё могут попасть в контекст. В обоих вариантах не пропускать страницы ради экономии и не считать короткий вывод доказательством, что связь между устройствами проверена.

Пример **одной страницы** для среды, где `functions.exec` предоставляет Linear MCP через `tools`. Подставить `run_id` из активного START; при следующей странице передать сохранённый `cursor` в `linear_list_comments`. Пример не заменяет обход всех страниц по правилам выше и проверку автора, актуальности, порядка и назначения.

```javascript
const runId = "<run_id>";
// Заполнить из блока состояния, включая назначения прежних запусков.
const completedAssignments = []; // { run_id, assignment_id, task }
const unresolvedAssignments = []; // { run_id, assignment_id, task }
const result = await tools.mcp__codex_apps__linear_list_comments({
  issueId: "NRT-90", limit: 3, orderBy: "createdAt" // Для полной сверки — 100.
});
if (result.isError) throw Error("Linear недоступен");
const page = result.structuredContent ?? JSON.parse(result.content[0].text);
const events = page.comments.filter((comment) => {
  const body = comment.body ?? "";
  if (!body.includes("DOCCHECK-NIGHTLY/") &&
      !/(?:^|\n)\s*type:\s*[A-Z_]+/m.test(body)) return false;
  const type = body.match(/(?:^|\n)\s*type:\s*([A-Z_]+)/)?.[1];
  const eventRun = body.match(/(?:^|\n)\s*run_id:\s*([^\s]+)/)?.[1];
  const previousRun = body.match(/(?:^|\n)\s*previous_run_id:\s*([^\s]+)/)?.[1];
  const assignment = body.match(/(?:^|\n)\s*assignment_id:\s*([^\s]+)/)?.[1];
  const task = body.match(/(?:^|\n)\s*task:\s*([^\s]+)/)?.[1];
  const globalTypes = ["START", "READY", "GO", "STOP", "STOPPED"];
  const assignmentTypes = ["ASSIGN", "ACK", "RESULT", "BLOCKED", "PAUSED_ACK", "CANCELLED_ACK",
    "RELEASED", "RELEASE_OLD", "ACCEPTED", "CHANGES_REQUESTED", "PAUSE",
    "CANCEL", "RESUME", "RENEW"];
  const malformed = (!globalTypes.includes(type) && !assignmentTypes.includes(type) &&
    type !== "QUEUE_ADD") || (assignmentTypes.includes(type) && !assignment) ||
    (type === "QUEUE_ADD" && !task) || (type === "RELEASE_OLD" && !previousRun);
  const retained = [...completedAssignments, ...unresolvedAssignments].some((entry) =>
    entry.run_id === (previousRun ?? eventRun) &&
    ((assignment && entry.assignment_id === assignment) ||
      (type === "QUEUE_ADD" && task && entry.task === task))
  );
  return !type || !eventRun || malformed || eventRun === runId ||
    globalTypes.includes(type) || retained;
}).map(({ id, createdAt, updatedAt, parentId, author, onBehalfOf, body }) =>
  ({ id, createdAt, updatedAt, parentId, author, onBehalfOf, body }));
text(JSON.stringify({
  page: page.comments.map(({ id, updatedAt }) => ({ id, updatedAt })),
  events, hasNextPage: page.hasNextPage, cursor: page.cursor
}));
```

Пример сохраняет сведения о границах страницы, показывает события текущего запуска, START/READY/GO/STOP/STOPPED других запусков, сообщения завершённых и неразобранных назначений из блока состояния и подозрительные неполные записи. Для фактической работы оба массива должны содержать актуальные данные из описания; пустой массив допустим только при отсутствии соответствующих записей. Наличие назначения в `unresolvedAssignments` означает необходимость его восстановить, а не разрешение на очистку комментариев. Не считать строковое совпадение подтверждением полномочий автора. Для полноценной сверки аналогично обработать остальные страницы, а уже обработанные события не выводить повторно; при недоступности такого исполнения использовать обычный MCP.
