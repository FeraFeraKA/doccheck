# Ночной режим DocCheck

Этот порядок предназначен для одного координатора и двух независимых рабочих чатов Codex на двух устройствах. Linear хранит краткое состояние, очередь и сообщения запуска; GitHub хранит ветки, PR и проверяемые версии. После подтверждённого завершения назначения его технические комментарии очищаются по protocol.md. Чаты не разделяют память; координатор и `worker-a` могут видеть один локальный каталог Николая, а `worker-b` работает в своей копии на Mac. Подготовка документа сама по себе не запускает агентов и не доказывает работу обновлённого порядка на двух устройствах.

Пошаговый запуск для двух людей описан в [инструкции участников](../../nightly/README.md).

## Границы

- Единственный координатор назначает задачи; один рабочий чат имеет не более одного активного назначения на изменение кода. Проверка чужого PR по запросу координатора не занимает второй кодовый слот и не меняет файлы автора. Заблокированное назначение можно приостановить и освободить слот только после безопасной передачи его состояния по протоколу. Работники не выбирают задачи самостоятельно из общего списка.
- Каждый исполнитель работает в своей локальной копии и ветке задачи. Координатор указывает для каждой задачи целевую согласованную или экспериментальную ветку и последовательно объединяет проверенные PR только в соответствующую цель. Прямой push в `main`, автодеплой и Done запрещены.
- Если координатор и `worker-a` используют один каталог, координатор не меняет его Git-состояние, а независимое ревью выполняется по конкретным коммитам и CI в GitHub. Изменяющуюся локальную копию нельзя выдавать за проверенный PR; при недостатке доказательств объединение блокируется.
- В текущем полноценном ночном запуске, если свободному worker нет готовых к назначению согласованных задач, координатор может создать отдельную экспериментальную ветку от последнего проверенного коммита ночной ветки и дать ему эксперимент, даже пока другие задачи выполняются или заблокированы. Отдельный ограниченный пилот запускается только по новому указанию Николая. Блокеры и незавершённые задачи остаются открытыми. Эксперименты не попадают в согласованную ветку и `main` без решения человека.
- Содержательный независимый отзыв на PR публикует противоположный worker; автор проверяет свои изменения до коммита и не публикует своё внутреннее ревью как отдельный отзыв. Координатор ждёт этот отзыв, завершённое Codex Code Review и необходимые CI на актуальных base/head по [порядку ревью](review.md). Если автоматическое Codex-ревью не запустилось, координатор вызывает `@codex review`. При объединении он передаёт GitHub ожидаемый проверенный head SHA; отказ или изменение базы требует повторной проверки. Устаревшие проверки, отсутствие проверок, недоступное ревью или необработанные замечания не считаются проходом.
- Выполнять применимые `AGENTS.md`, CONTRIBUTING и `docs/data-policy.md`. Никаких секретов, закрытых данных, OCR-текста, реальных результатов или независимого эталона в сообщения, PR и логи. Не читать историю старых описаний ради ожидаемых ответов.
- Ошибки окружения, другой ОС или временные сбои сначала устранять по [порядку действий при сбоях](communication.md#сбои-и-продолжение-работы); один блокер не завершает весь запуск. Остановку по команде Николая или исчерпанию лимита соблюдать. При недоступности Linear/GitHub, конфликте владельцев, неизвестном результате проверки или потере сессии не угадывать состояние и не переназначать занятую задачу автоматически; координатор фиксирует блокер и продолжает независимую работу.

## Важное ограничение запуска

Комментарий в Linear сам по себе не запускает другой чат. В активной работе каждый чат проверяет события по необходимости, без самостоятельного периодического опроса. Запасной механизм — короткое плановое продолжение каждого уже открытого чата Codex каждую минуту, создаваемое из этого чата его владельцем по инструкциям `macos.md`. Продолжение не гарантирует прерывание выполняющегося действия или доставку за минуту. Каждая проверка учитывает пару `run_id` и `assignment_id` и не создаёт новый рабочий процесс вручную. Проверить фактическую доступность продолжений, доставку и возвращение результата на обоих устройствах: обычный одноразовый промпт может завершиться, а повторный запуск без состояния может сделать работу дважды. Если плановое продолжение недоступно, не объявлять автоматический режим работающим и не подменять его ручной проверкой.
