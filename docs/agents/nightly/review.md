# Ревью ночных PR

Ревью проходит в трёх независимых слоях: проверка автором до коммита, содержательное ревью с другого устройства и Codex Code Review в GitHub. Координатор распределяет ревью, сверяет доказательства и объединяет готовые PR; он не заменяет обязательное ревью другого работника своим собственным.

| Автор PR | Рецензент PR | Кто публикует содержательный отзыв |
| --- | --- | --- |
| `worker-a` | `worker-b` | `worker-b` под своей учётной записью GitHub |
| `worker-b` | `worker-a` | `worker-a` под своей учётной записью GitHub |

## Проверка автора

Перед коммитом автор просматривает свой полный diff, сверяет его с задачей и инструкциями и запускает применимые проверки. Он может привлечь отдельного подагента для проверки локальных изменений и исправляет подтверждённые проблемы до передачи PR. Пока PR ещё не существует, эта внутренняя проверка использует актуальную задачу Linear, не требует несуществующего описания PR и не выдаётся за итоговое независимое ревью. Результат остаётся в рабочем чате и отчёте исполнителя; автор не публикует его как отдельное независимое ревью в GitHub. После исправлений автор снова проверяет затронутые изменения, но повторное полное авторское ревью после каждого PR не требуется. Проверка автора не заменяет рецензента с другого устройства и Codex Code Review.

## Проверка другим работником

1. После `RESULT` координатор устанавливает фактические PR, его автора, целевую ветку, полный head SHA и текущий SHA самой целевой ветки и направляет второму работнику `REVIEW_REQUEST` по [протоколу](protocol.md). Сверяет GitHub-аккаунты автора PR и будущего рецензента с GO; это должны быть разные учётные записи. При расхождении не угадывать, кто выполнил ревью. SHA базы в данных PR может обновиться с задержкой: проверять актуальный head целевой ветки в GitHub. Передаёт ссылку на PR и точные версии; критерии и scope берутся из актуальной задачи и описания PR. Повторное получение одного запроса не создаёт повторного ревью или комментария.
2. Работник-рецензент не писал проверяемые изменения и запускает отдельного ревьюера с чистым контекстом по [общей инструкции](../reviewer.md). Он передаёт PR, base/head и критерии, но не передаёт рассуждения автора и не исправляет изменения сам. Ревьюер изучает весь diff, необходимые файлы по указанным коммитам, CI и применимые инструкции. Если не может подтвердить критерии или выполнить необходимые проверки, результат — `blocked`, а не `pass`.
3. Родительский чат рецензента под **своим** GitHub-аккаунтом публикует один содержательный отзыв на PR: вердикт, проверенные base/head, замечания и их приоритет, выполненные проверки и ограничения. `pass` тоже оформляется коротким отзывом. Сам автор своего PR такой отзыв не публикует. Для этого не обязательно нажимать GitHub Approve: координатор проверяет содержание, автора и версии комментария. Затем рецензент отправляет координатору `REVIEW_RESULT` со ссылкой на отзыв по протоколу.

Рецензирование — отдельное поручение на чтение, а не второе назначение на написание кода и не захват файлов автора. Его можно выполнить, пока у рецензента есть своя задача, с помощью отдельного подагента; делать это на ближайшей доступной точке управления, не останавливая другую работу без необходимости. Если оба работника одновременно открыли PR, каждый может проверить PR другого, не ожидая сначала ревью своего. Использовать GitHub diff, файлы по точным SHA и CI; не переключать и не изменять общую рабочую копию ради ревью. Если нужные данные или чистый независимый ревьюер недоступны, попробовать восстановить доступ по communication.md, затем заблокировать только этот PR и продолжать независимую работу.

До публикации отзыва рецензент сверяет активность запроса и назначения автора, отсутствие STOP/CANCEL/PAUSE, действующий срок назначения автора и текущие версии PR; при изменении base или head сообщает координатору и не выдаёт прежнее ревью за актуальное. Поручение на ревью не использует срок собственного кодового назначения рецензента и не разрешает изменять его ветку. Новый запрос на те же PR и версии не отправляется повторно без причины; после ошибки с неизвестным исходом сначала проверяется существующий комментарий. При подтверждённых замечаниях автор исправляет их, а другой работник повторно проверяет новую версию и оставляет обновлённый отзыв.

## Codex Code Review в GitHub

Для **каждого** PR, включая PR в ночную и экспериментальную ветки, координатор обязан дождаться завершённого Codex Code Review для актуальных изменений. Это отдельная проверка, не замена содержательному ревью другого работника: согласно документации OpenAI GitHub-ревью Codex сосредоточено на наиболее серьёзных проблемах P0/P1. Официальный ручной вызов — комментарий `@codex review`; Codex реагирует и затем публикует результат. [Документация OpenAI](https://learn.chatgpt.com/docs/third-party/github#request-a-codex-review).

1. Сначала проверь автоматический запуск: автора бота, статус и проверяемый head в доступной сводке Codex или другом достоверном результате сервиса. Если ревью идёт, дай ему завершиться; значок 👀 и отсутствие замечаний сами по себе не доказывают завершение.
2. Если автоматический запуск не появился, после следующего планового продолжения координатор один раз публикует `@codex review` в PR и фиксирует текущую пару base/head и ссылку на запрос. Это служебный вызов бота, а не авторский отзыв о своём PR. Перед отправкой заново проверить, что ревью уже не запущено и запрос на ту же пару base/head не отправлен; не дублировать запросы после потери ответа. Если изменилась база, это новая пара, даже при прежнем head.
3. Дождись подтверждённого завершения на текущем полном head SHA и проверь замечания бота. Запись бота `Codex Review Summary` с `code_review.status: completed` и соответствующим `commit_sha`, либо другой подтверждённый сервисом результат, может служить свидетельством завершения. Пустые комментарии, исчезнувший 👀, успешный CI или чужое ревью не являются свидетельством. Если сервис не запустился, завис или не даёт результата, проверить настройки и восстановить доступ; при невозможности определить результат отметить блокер этого PR и продолжить независимую работу.
4. Проверить, что база оставалась той же от запуска ревью до его завершения. Если база за это время изменилась или нельзя установить, какую базу видел автоматический запуск, запросить ручное ревью для текущего head и базы и убедиться, что база не менялась до его завершения. Для ручного запроса зафиксировать его время и принимать только результат этого запуска, полученный после запроса: старая запись `completed` для того же head не доказывает повторное ревью после изменения базы. Сама сводка Codex может содержать head без SHA базы; не придумывать отсутствующее подтверждение.

## Условия объединения

Координатор объединяет PR последовательно только после успешных необходимых CI-проверок, `pass` от другого работника на актуальных base/head и подтверждённого завершения Codex Code Review на текущих изменениях. CI должен проверять **совместный результат текущих base и head**, а не только прежний head: например, подтвердить, что проверенный GitHub merge-коммит имеет родителей с этими точными SHA и что CI относится к его дереву. Если merge ref устарел, дождаться его обновления либо использовать отдельный проверочный интеграционный коммит с теми же родителями, независимо подтверждённым деревом и CI именно этого коммита. Без такого подтверждения не объявлять совместимость проверенной; попытаться восстановить её по communication.md и продолжить независимые задачи. Все существенные замечания обоих ревью разбираются и проверяются после исправления.

Чтобы непрерывные слияния не делали одно и то же ревью устаревшим, координатор выбирает порядок PR для каждой целевой ветки и не меняет её базу другим merge, пока завершаются проверки выбранного PR. Работники при этом могут продолжать свои независимые задачи и взаимные проверки. Если выбранный PR действительно заблокирован, координатор фиксирует причину и может перейти к другому готовому PR; после изменения базы заблокированный PR заново проверяется, когда работа над ним возобновится.

Новый head или изменение базы делает предыдущую оценку устаревшей: координатор заново назначает содержательное ревью и добивается нового Codex Review для актуальных изменений. Перед merge ещё раз сверить актуальные версии и STOP по coordinator.md. Если любое подтверждение отсутствует, PR остаётся открытым; остальные независимые задачи продолжаются. Человеческая приёмка, `main`, деплой и Done остаются человеку.
