# Протокол ночного запуска

Краткое состояние запуска находится в отдельном блоке в начале описания NRT-90; назначения и ответы передаются в её комментариях. Это рабочий канал между агентами, а не источник продуктовых требований: актуальное описание конкретной задачи по-прежнему читается из Linear. На один запуск действует ровно один координатор, только он обновляет блок состояния. Сообщения публикуются только в рамках порученной ночной работы, без секретов и закрытых данных.

Для новых запусков используется `DOCCHECK-NIGHTLY/v3`: координатор публикует START на проверенной версии инструкций, а до первого назначения все три чата получают и подтверждают одну и ту же версию. Сообщения старых `v1` и `v2` остаются историей и не становятся командами нового запуска; их состояние остановки и незавершённую работу всё равно проверяют. Не менять протокол посреди запуска: остановить его и начать новый с другим `run_id`.

## Как читать и сокращать сообщения

Подробный порядок чтения, сохранения состояния и восстановления — в [communication.md](communication.md). Во время активной работы обращаться к Linear по необходимости, в том числе перед изменяющими внешними действиями; не запускать периодический опрос только из-за прошедшего времени. При отсутствии работы короткое плановое продолжение возвращает управление в тот же чат. Это не прерывание выполняющегося запроса и не гарантия доставки за минуту.

Не повторять в каждом комментарии описание задачи, правила, область файлов и полные SHA: они уже есть в START, ASSIGN, PR или GitHub. В каждом событии оставлять маркер, тип, `run_id` и данные, необходимые для его однозначной связи с назначением и обработки. Пока назначение активно, технические сообщения не редактировать и не удалять: исправление публиковать новым событием. После подтверждённого завершения их удаляют по [порядку очистки](communication.md#очистка-завершённой-задачи). Свободный текст в NRT-90 сам по себе не меняет состояние протокола; команды пользователя в чате и оформленный по протоколу STOP по-прежнему действуют.

Для читаемости `run_id` может выглядеть как `n90-20261112-1953`, а `assignment_id` — как `a1`, `b1`, `a2`. `run_id` должен быть уникален для запуска, `assignment_id` — внутри него; назначение определяется парой этих идентификаторов. Перед созданием проверить отсутствие совпадения в истории, при совпадении выбрать другой ID. Точные полные SHA по-прежнему обязательны там, где устанавливается и проверяется версия; короткий SHA не является заменой.

## Сообщение запуска

Координатор создаёт запись с маркером `DOCCHECK-NIGHTLY/v3`, типом `START`, уникальным `run_id`, текущим UTC-временем, репозиторием, именем и полным SHA ночной ветки, идентификаторами `worker-a` и `worker-b`, допустимым набором согласованных задач, условиями остановки и `mode`. Для текущего полноценного запуска использовать `mode: nightly`; отдельный `mode: pilot` допустим только по новому прямому указанию Николая. Указать ID учётной записи координатора в Linear и способ связи. Старые запуски не возобновляются без явной проверки координатором.

Сразу после START, до приглашения рабочих чатов, координатор создаёт или заменяет и проверяет блок состояния текущего запуска в описании NRT-90 по communication.md. Каждый рабочий чат проверяет свой ID в Linear через `get_user` с `me`, свой GitHub ID и login через `github_get_user_login` и публикует верхнеуровневый `READY` с маркером, `run_id`, своим `worker`, полным фактическим `base_sha` полученной версии инструкций и GitHub ID/login. Затем сообщает человеку об учётных записях и готовности. Когда оба рабочих чата подтвердили доступ и версию инструкций, а Николай сообщил координатору, что можно начинать, координатор сверяет авторов READY с участниками запуска, оба `base_sha` с START и разные **Linear и GitHub** учётные записи двух работников. Координатор может использовать ту же учётную запись, что и worker-a. Затем публикует `GO` с маркером, типом, `run_id` и подтверждёнными ID учётных записей Linear и GitHub для каждого слота. Если идентичность слота, разные аккаунты работников или версия инструкций не установлены, GO и назначения не выдаются. Действительно только GO от указанной в START учётной записи координатора; до действующих START и GO назначения не выдаются и не выполняются. Перед публикацией проверить, что STOP и GO для запуска ещё нет; после восстановления проверять GO в Linear, а не предполагать готовность по молчанию в чате.

```text
DOCCHECK-NIGHTLY/v3
type: READY
run_id: n90-20261112-1953
worker: worker-a
base_sha: <полный SHA проверенных инструкций>
github_id: <ID GitHub-аккаунта>
github_login: <логин GitHub>
```

```text
DOCCHECK-NIGHTLY/v3
type: GO
run_id: n90-20261112-1953
worker_a_author: <Linear user ID>
worker_b_author: <Linear user ID>
worker_a_github: <GitHub user ID>
worker_b_github: <GitHub user ID>
```

Для `mode: nightly` координатор ведёт всю согласованную очередь: сначала назначает доступные независимые задачи, по мере завершения проверенных зависимостей выбирает следующие и продолжает работу без отдельного разрешения после первых двух задач. Если для согласованной очереди понадобятся отсутствующие результаты прошлой ночной ветки, их исходные NRT-ID указываются в START как разрешённые источники переноса, а не как новые тестовые задачи. Если Николай отдельно попросит `mode: pilot`, заранее согласовать две независимые задачи; новые задачи и эксперименты в таком пилоте не назначать. Для `nightly` эксперименты разрешены по условиям ниже.

В `mode: nightly` для новой экспериментальной идеи координатор сначала создаёт отдельную задачу в Backlog и публикует в NRT-90 запись `QUEUE_ADD` с маркером, `run_id`, полем `task: NRT-<номер>`, `work_kind: experiment` и целью. После этого задача становится допустимой для данного запуска. Работник сверяет QUEUE_ADD с действующим координатором и run_id перед исполнением; согласованные задачи нельзя добавлять в очередь этим способом без разрешения Николая. В пилоте `QUEUE_ADD` не используется.

## Назначение

Для каждого задания координатор публикует отдельный комментарий с маркером `DOCCHECK-NIGHTLY/v3` и полями:

```text
DOCCHECK-NIGHTLY/v3
type: ASSIGN
run_id: <идентификатор запуска>
assignment_id: <уникальный идентификатор назначения>
worker: worker-a | worker-b
task: NRT-<номер>
work_kind: agreed | experiment
work_mode: new | continue | carry
base_branch: <ночная ветка для agreed или экспериментальная ветка для experiment>
base_sha: <полный SHA целевой ветки на момент назначения>
task_branch: <отдельная ветка задачи>
paths: <выделенные пути или границы>
valid_until: <UTC-время действия назначения>
```

Цель, критерии, зависимости и способ проверки брать из актуальной задачи Linear; отдельно указывать только изменения и ограничения именно этого назначения. `base_sha` фиксирует версию целевой ветки при назначении: если ветка с тех пор продвинулась обычным fast-forward, работа может начаться с назначенного коммита, а ревью и интеграция проводятся на актуальной базе по review.md. При несовместимой истории или неизвестном состоянии не угадывать. Назначение считается действительным, только если совпадает с активным START и GO, адресовано этому worker, создано действующим координатором и не приостановлено, не отменено и не завершено. В пилоте работник дополнительно сверяет ID задачи с двумя задачами START и отклоняет эксперимент. `PAUSE` делает ASSIGN неактивным до явного действующего `RESUME`; `CANCEL` или `STOP` закрывает его. При неоднозначности не приступать. Координатор назначает задачу одному worker и не перекрывает файлы одновременно без явного согласования.

Для новой работы с `work_mode: new` `task_branch` создаётся от `base_sha`. Для продолжения неразобранной работы после STOP координатор выдаёт **новое** `assignment_id` с `work_mode: continue`, прежними `previous_run_id` и `previous_assignment_id`, существующими `task_branch` и `pr`, прежним исходным SHA, текущим `base_sha` целевой ветки и точным head сохранённой ветки. Назначение получает первоначальный работник после проверки его локального состояния. Автоматически передавать другому worker ветку или PR с уже написанными изменениями нельзя: оба работника стали бы авторами и независимого рецензента не осталось бы. При недоступности первоначального работника сохранить работу, обозначить блокер этой задачи и продолжать независимую очередь; нестандартную передачу согласовать с Николаем. Если изменений ещё нет, передачу можно рассмотреть после подтверждения безопасной остановки и отсутствия потерянной работы. Такой ASSIGN ссылается на уже существующую ветку и открытый PR, а не создаёт их заново; если PR направлен в прежнюю ночную ветку, его базу меняют на назначенную новую и заново проверяют. Если ветки или PR ещё не было, координатор явно указывает, что именно нужно создать, после проверки отсутствия дубликатов.

Для переноса уже проверенного результата, слитого в **другую** ночную ветку и отсутствующего в новой, после GO можно выдать первоначальному автору `work_mode: carry` с новой веткой от назначенного `base_sha`, ссылкой `source_pr`, полными `source_base_sha` и `source_head_sha` исходного PR и `previous_run_id`/`previous_assignment_id`. Это перенос существующего diff, а не повторное выполнение тестовой задачи и не перевод исходной задачи из In Review в Done. Автор сверяет содержимое и область изменений с исходным PR и открывает PR переноса в новую ночную ветку только если для этой цели ещё нет открытого PR; уже слитый старый PR не переоткрывается и не выдаётся за новый. Другой worker и Codex проверяют актуальный PR переноса, CI проверяет новую интеграцию. Если первоначальный автор недоступен или содержимое/независимость не подтверждены, не передавать его написанную работу другому worker автоматически; оставить зависимость заблокированной и продолжать независимые задачи. Источник, итоги и ограничения переноса явно указать в PR.

## Поручение на ревью

Для PR автора координатор публикует отдельный `REVIEW_REQUEST` второму worker по [порядку ревью](review.md). Это не второе назначение на написание кода и не освобождает занятый слот; ревью не меняет чужие файлы или ветку. `assignment_id` относится к задаче **автора**, а `worker` — к противоположному работнику-рецензенту. `review_id` уникален внутри `run_id` для данной попытки и версий; новый base или head получает новый `review_id`.

```text
DOCCHECK-NIGHTLY/v3
type: REVIEW_REQUEST
run_id: <идентификатор запуска>
assignment_id: <назначение автора>
review_id: <идентификатор ревью>
worker: <другой worker>
pr: <ссылка на PR>
base_sha: <полный SHA целевой ветки>
head_sha: <полный SHA PR>
```

После независимой проверки и публикации содержательного отзыва рецензент отправляет `REVIEW_RESULT` с теми же `run_id`, `assignment_id`, `review_id` и своим `worker`, вердиктом `pass`, `changes_requested` или `blocked` и ссылкой на GitHub-отзыв. Если публикация недоступна, указывает причину `blocked` без выдуманной ссылки. Координатор сверяет оба сообщения с активным назначением, идентичностью слота в GO, GitHub-автором отзыва и точными версиями из запроса и отзыва. Автор PR не может выступать рецензентом этого PR; результат ревью не освобождает и не меняет собственное назначение проверяющего. Если состояние или результат изменяющего запроса неизвестны, сначала восстановить их по communication.md, не создавать повторный отзыв.

## Подтверждение и результат

Работник создаёт отдельный верхнеуровневый комментарий с тем же маркером, `run_id`, `assignment_id`, своим `worker` и одним типом. Не использовать ответ внутри чужого комментария: это упростит безопасную очистку.

Координатор сверяет `author.id` ответов `ACK`, `RESULT`, `BLOCKED`, `PAUSED_ACK`, `CANCELLED_ACK`, `RELEASED`, `REVIEW_RESULT` и `STOPPED` с учётной записью указанного слота из GO, а также `run_id` и `assignment_id`, где он требуется. Для `REVIEW_RESULT` указан противоположный работник-рецензент, не автор назначения. Если STOP произошёл до GO, подтверждение STOPPED сверять с автором READY этого слота и подтверждённым участником; при отсутствии подтверждения сохранять слот занятым до безопасной ручной проверки. Одной надписи `worker-b` в тексте недостаточно. Если используется `onBehalfOf` или автор не совпадает с подтверждённой учётной записью, не считать подтверждение действительным до выяснения полномочий. Координатор и worker-a могут использовать один аккаунт: совпадение ID само по себе не доказывает, какой из их чатов отправил сообщение; при неоднозначности не освобождать слот.

- `ACK` — назначение принято и проверено по указанным версиям. Для `new` и `carry` `base: ok` означает, что новая ветка создана от полного `base_sha`; когда она появится на GitHub, координатор проверяет исходный коммит. Для `work_mode: continue` работник отправляет `continuation: ok` после проверки прежней ветки, её head и исходной базы вместе с текущим `base_sha` целевой ветки; он не утверждает, что старая ветка создана от новой базы. ACK не доказывает завершения работы.
- `RESULT` — ссылка на PR, полный проверяемый head SHA, краткие ограничения, если есть. Изменённые пути, команды, фактические результаты и статус Linear находятся в PR и отчёте; их не нужно дублировать в комментарии.
- `BLOCKED` — причина, что необходимо для продолжения, состояние своей ветки, PR и локальных изменений; секреты и закрытые данные не включать.
- `PAUSED_ACK` — работник подтвердил приостановку назначения и может безопасно начать другое без потери своей работы; указать, где сохранено состояние.
- `CANCELLED_ACK` — работник подтвердил, что отменённое назначение больше не выполняется, его ветка, PR и локальные изменения сохранены и исход уже отправленных запросов установлен. Указать, где сохранено состояние; отмена назначения не отменяет автоматически Linear-задачу и не откатывает уже выполненный merge.
- `RELEASED` — работник увидел зафиксированный координатором итог принятого назначения, завершил работу по нему и подтвердил номер версии именно этого итога (`result_revision`); его рабочую копию можно безопасно использовать для другого задания. При неопределённом локальном состоянии или незавершённом запросе вместо этого сообщить блокер.

Координатор записывает решение `ACCEPTED`, `CHANGES_REQUESTED`, `PAUSE` или `CANCEL` с теми же идентификаторами, PR и проверенным SHA, когда он есть. После ACCEPTED слот выполненного назначения освобождается только после `RELEASED` и подтверждённого обновления блока состояния. Координатор может выдать `PAUSE` после `BLOCKED` либо для выполняющегося эксперимента, когда появилась приоритетная согласованная задача; в обоих случаях прежняя работа остаётся незавершённой. Для приостановленного назначения слот освобождается после `PAUSED_ACK` и проверки, что предыдущая работа не потеряется; при неясном состоянии слот остаётся занятым.

После `CANCEL` работник не начинает новые действия по отменённому назначению, проверяет и сохраняет результаты и отправляет `CANCELLED_ACK` либо `BLOCKED`, если не может безопасно подтвердить состояние. Координатор проверяет автора и состояние, фиксирует отмену и место сохранения работы в блоке NRT-90 и освобождает соответствующий слот только после подтверждения. Если это отмена ранее приостановленного назначения, а слот уже занят другой задачей, его текущая занятость не меняется; работник проверяет сохранённое состояние прежнего назначения, не переключая и не перезаписывая текущую работу. Прежнее назначение не возобновляется; повторное назначение той же задачи возможно только после проверки ветки, PR и сохранённых изменений, с новым `assignment_id`. Отменённая работа не считается завершённой или принятой. Новое назначение выдаётся после завершения, безопасной приостановки или подтверждённой отмены предыдущего. Использовать идентификаторы, а не время комментария, чтобы повторная проверка очереди не запускала одну работу дважды.

Пример короткого подтверждения и результата:

```text
DOCCHECK-NIGHTLY/v3
type: ACK
run_id: n90-20261112-1953
assignment_id: a1
worker: worker-a
base: ok
```

```text
DOCCHECK-NIGHTLY/v3
type: RESULT
run_id: n90-20261112-1953
assignment_id: a1
worker: worker-a
pr: <ссылка на PR>
head_sha: <полный SHA проверенного коммита PR>
```

В примере `RESULT` ограничений нет; при их наличии добавить короткое поле `limitations`. `BLOCKED` и `PAUSED_ACK` должны содержать сведения для безопасного сохранения работы. В `ACCEPTED` зафиксировать полный SHA результата объединения. Один и тот же идентификатор ссылки или SHA не нужно повторять в пояснительных абзацах.

В режиме `nightly`, если свободному worker нет готовых согласованных задач, координатор может назначить эксперимент в отдельной экспериментальной ветке от последнего проверенного head, указав этот факт в ASSIGN и сохранив в отчёте заблокированные задачи. Для каждого эксперимента создаётся отдельная задача Linear в Backlog со своим NRT-ID; назначение и In Review эксперимента не меняют статус исходной заблокированной задачи. Это не отменяет её и не разрешает слияние эксперимента в согласованную ветку. При разблокировке согласованная задача возвращается в приоритетную очередь.

Для experiment `base_branch` — только экспериментальная ветка; PR эксперимента направляется только в неё. Для agreed `base_branch` — согласованная ночная ветка. Работники не направляют свои PR в `main`. Координатор может открыть обзорный PR согласованной ночной ветки в `main` для человека, но не мёржит его. Координатор отклоняет PR с базой, не соответствующей `work_kind`; никакой режим не разрешает автоматическое объединение эксперимента в согласованную ветку.

Когда блокер снят и прежнее назначение приостановлено, координатор может выдать `RESUME` с прежними `run_id`, `assignment_id`, `worker`, веткой задачи, актуальной базой и новым `valid_until`, только если слот свободен. То же относится к эксперименту, приостановленному ради приоритетной задачи: его можно возобновить, когда слот снова свободен и нет готовой приоритетной работы. Если worker занят экспериментом, сначала безопасно приостановить или завершить его и получить подтверждение. Продолжать написанную работу может первоначальный работник после проверки сохранённого состояния; автоматически передавать её другому worker нельзя, чтобы сохранить независимость взаимного ревью. Когда изменений ещё нет, передачу рассматривать только после безопасной остановки и проверки сохранности. Продолжение не создаёт повторный PR и проходит актуальные проверки заново.

Отсутствие ACK или сообщения по таймеру не доказывает, что агент остановился: перед переназначением координатор проверяет PR, ветку, состояние устройства и фиксирует решение. Два действующих координатора, несколько активных назначений одному слоту или конфликтующие назначения одного файла — блокер, а не повод выбирать произвольно. `STOP` закрывает текущий запуск; новый START создаётся с новым `run_id`.

Координатор указывает ограниченный срок `valid_until`: для первого назначения — 30 минут от назначения. Пока он работает, он продлевает только незавершённые назначения отдельным сообщением `RENEW` с `run_id`, `assignment_id`, `worker` и новым UTC-временем, не реже чем за 10 минут до окончания. Для контроля срока используются локальные часы при доступном управлении; отдельный периодический опрос Linear во время активной работы не создаётся. Если управление долго недоступно, продление может не состояться вовремя. Назначение с уже объединённым PR, но без `RELEASED` и освобождения слота, остаётся незавершённым для продления. Работник использует последнее действующее продление от координатора. После истечения срока работник сохраняет локальное состояние и не выполняет push, PR или смену статуса до подтверждённого продления. Истечение не означает, что задачу можно назначить другому устройству: незаписанные изменения могут оставаться у первого. Время и срок проверяются до побочных действий; недоступные часы или неоднозначное продление — блокер.

По команде Николая или при штатном завершении координатор публикует `DOCCHECK-NIGHTLY/v3`, `type: STOP`, `run_id` и причину в NRT-90. Сам Николай также может разместить такое сообщение в NRT-90. Работник признаёт STOP только от учётной записи, указанной в START, или Николая; прекращает новые действия, сохраняет состояние и проверяет результат уже отправленных запросов. Затем отключает своё плановое продолжение и публикует `STOPPED` со своим `worker`, `run_id` и результатом отключения. Для каждого своего незавершённого назначения на момент STOP, включая приостановленные, дополнительно указать `assignment_id`, задачу, ветку, PR, где сохранены локальные изменения, и неопределённые действия; при отсутствии работы указать это явно. Если отключение или исход запроса не удалось подтвердить, указывает это в `STOPPED` как блокер; слот нельзя считать безопасно освобождённым. Повторное сообщение того же слота не заменяет подтверждение другого.

Остановка только чата координатора не уведомляет другие устройства: если он не может опубликовать STOP из-за сбоя или лимита, новые действия работников прекращаются после истечения назначения; Николай может опубликовать STOP самостоятельно. Уже запущенный запрос не гарантированно отменяется. Перед повторным использованием слотов для другого запуска проверить завершение старой работы и отключение продолжений по [порядку обмена](communication.md).

Пример команды остановки в комментарии NRT-90:

```text
DOCCHECK-NIGHTLY/v3
type: STOP
run_id: <идентификатор текущего запуска>
reason: Остановлено Николаем
```

После перезапуска рабочий агент сначала сверяет назначения, ранее отправленные ACK/RESULT/BLOCKED, свою локальную ветку, незакоммиченные файлы и существующий PR. Он продолжает только однозначно опознаваемую свою работу, не создаёт повторно ветку или PR, не выполняет reset/stash и не перезаписывает изменения. Если владельца файлов или состояние другого устройства определить нельзя, отправляет BLOCKED и сохраняет рабочее состояние. Координатор не назначает ту же задачу другому работнику, пока не выяснена судьба прежней работы.

Перед push, созданием или обновлением PR, сменой статуса Linear и объединением координатор и работник заново проверяют отсутствие STOP и CANCEL и то, что назначение не приостановлено событием PAUSE без последующего RESUME. Публикация `CANCELLED_ACK` или `BLOCKED` после CANCEL разрешена для передачи фактического состояния, даже если срок отменённого назначения истёк; это не разрешает продолжить работу по нему. Продлевать отменённое назначение ради такого подтверждения не требуется. Если пришёл общий STOP, он имеет приоритет и работник выполняет порядок STOP/STOPPED. При недоступности канала не выполнять зависимые внешние действия. STOP, CANCEL или PAUSE не гарантирует мгновенной отмены уже отправленного запроса: зафиксировать его фактический результат и не начинать следующие действия.
