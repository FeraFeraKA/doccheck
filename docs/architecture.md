# Границы архитектуры

Планируемый путь данных:

```text
бухгалтер: КФЗ и первичные документы → UI → FastAPI → PostgreSQL (задание)
                                            ↓
                                  локальное хранилище файлов
                                            ↓
                                    Python worker
                                            ↓
     извлечение → сопоставление → сводные значения → сверка с КФЗ
                                            ↓
                       результат и ссылки на первичные источники
                                            ↓
                                 PostgreSQL → API → UI
```

Пользовательский сценарий и открытые вопросы описаны в
[уточнении кейса](case/README.md). Формат промежуточной сводки и необходимость
отдельного файла ещё не определены. Сводные значения должны сохранять
подтверждение первичными документами.

API не выполняет OCR в HTTP-запросе. Отдельный worker резервирует задания в
PostgreSQL; начальная параллельность обработки — один пакет. Это ограничение
процесса приложения, а не число агентов разработки. Оригиналы и превью хранятся
на диске; база хранит задания, метаданные и результаты. Расчёты, правила и выбор
относящихся к договору и периоду документов выполняются в Python. UI показывает
результат, доказательства и возможные причины без пересчёта денежных сумм.

В `main` есть синтетический каркас UI, FastAPI, PostgreSQL, worker и Compose,
а также версионированный [контракт результата](../contracts/README.md) и
HTTP-контракт. Это техническая основа, не человеческая приёмка и не доказательство
готового OCR, загрузки файлов или реальной финансовой сверки. Переданный
[ML-модуль](ml-module-audit.md) обрабатывает подготовленные наблюдения;
фактические возможности и интеграция проверяются отдельно с Семёном.
