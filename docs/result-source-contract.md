# Контракт результата сверки и доказательств

Версия `doccheck-check-result/1` описывает обмен между обработчиком, API и UI. Обработчик рассчитывает результат и сохраняет его вместе с адресами доказательств. API передаёт сохранённые значения, а UI показывает их и открывает источники. Для NRT-86 и NRT-18 этот документ задаёт семантику общей машинной схемы и моделей. Присланная JSON Schema 0.1 рассматривается как предложение. Утверждение владельцами обработки и интеграции проводится отдельно после технического ревью. [NRT-85](https://linear.app/andreiakimov/issue/NRT-85/soglasovat-minimalnyj-kontrakt-rezultata-i-istochnikov) · [Схема и пример](https://linear.app/andreiakimov/issue/NRT-86/pydantic-i-sinteticheskij-primer-soglasovannogo-kontrakta)

## Результат задания

| Поле | Значение |
| --- | --- |
| `schema_version` | `doccheck-check-result/1`. Изменение смысла поля или статуса требует новой версии. |
| `run_id` | Идентификатор задания, к которому относится сохранённый результат. |
| `synthetic` | `true` для искусственного примера, `false` для рабочего пакета. UI явно помечает синтетику. |
| `scope` | `report_document_id`, `contract_number`, `period_start`, `period_end` и `report_row_locator`. Диапазон дат включительный. Пользователь или утверждённый профиль явно выбирает область перед запуском. |
| `versions` | `code_revision`, `rules_version`, `ml_module_version`, `ml_policy_version`, `model_revision`. Фиксируются фактически использованные версии. `null` у неприменимого компонента. |
| `documents` | Реестр отчёта и первичных файлов с результатами чтения и решениями об использовании. |
| `evidence` | Адресные наблюдения с ID, на которые ссылаются строки, расчёты и причины. |
| `rows` | Показатели отчёта, их значения, доказательства и результаты сверки. |
| `summary` | Сводка по статусам строк, первичным причинам и зависимым последствиям. |

API хранит состояние выполнения задания отдельно. `queued` означает ожидание, `processing` обработку, `completed` сохранённый результат, `completed_with_issues` сохранённый результат с частичным техническим сбоем, `failed` отсутствие пригодного результата из-за ошибки задания. Подтверждённое денежное расхождение может быть в `completed`. При недоступности отдельного файла обработчик продолжает работу, если оставшиеся данные пригодны. Переходы, маршруты и повтор запросов уточняются в [NRT-13](https://linear.app/andreiakimov/issue/NRT-13/kontrakt-api-i-moki-dlya-fronta).

### Документы

У каждого файла есть `id`, `name` для отображения, `sha256` исходных байтов, `format` (`pdf`, `png`, `xlsx`, `docx`), `role` (`report` или `support`), `parse_status` и `decision`. У принятого файла неизвестного формата `format` может быть `null` с ошибкой `unsupported_format`. `parse_status` принимает `pending`, `parsed`, `partial`, `error`. `decision` содержит `state`, `reason_code`, понятное пояснение `message` и `evidence_refs`. `errors[]` хранит безопасный код и сообщение об ошибке файла. Источники открываются через ID документа в рамках задания. У документа отчёта `include` означает, что он служит источником отчётных значений.

| `decision.state` | Смысл |
| --- | --- |
| `include` | Есть пригодные данные для отчётного значения или слагаемого. Допуск каждой конкретной суммы описывается в строке результата. |
| `exclude` | Есть основание исключить файл, например другой договор, другой период или побайтовая копия. Для копии сохраняется ссылка `duplicate_of` на представителя. |
| `needs_review` | Связь, версия или возможный дубль неоднозначны. Сохраняются кандидат и причины. |
| `parse_error` | Из файла не удалось получить пригодные данные. Причина сохраняется в `errors`. |

В `evidence` остаются ссылки на версию файла с проверенным SHA. Изменившийся файл требует нового чтения. Для группы побайтовых копий обработчик выбирает один экземпляр и сохраняет его ID в `duplicate_of` остальных экземпляров. Все экземпляры видны в реестре. Из представителя каждая отдельная подтверждённая и допустимая операция входит в расчёт один раз. Две разные операции с одинаковой суммой остаются двумя слагаемыми. Совпадение номера или суммы при разном SHA даёт повод проверить связь и версии. Правила тождества операций между разными файлами и замены версий определяются отдельно.

### Показатели и полнота

| Поле строки | Значение |
| --- | --- |
| `id`, `label`, `indicator_code` | ID строки результата, подпись показателя и код при наличии. Ссылка на строку/колонку отчёта сохраняется в `reported_evidence_refs`. |
| `unit`, `reported_value` | Единица измерения и значение из отчёта. Если оно отсутствует или не читается, значение `null` и указывается причина. |
| `observed_evidence_sum` | Сумма допущенных слагаемых из доступных доказательств. `null` при отсутствии слагаемых. Доказанный ноль передаётся как `"0.00"`. |
| `expected_value` | Полное ожидаемое значение по правилу при достаточных доказательствах. При неполной или неизвестной первичке `null`. Может сохраняться, когда не удалось прочитать отчётное значение. |
| `delta` | `reported_value − expected_value` в Python при допустимом сравнении. При `unverified` всегда `null`. |
| `status`, `reasons[]` | Результат проверки, коды причин, пояснения и ссылки на относящиеся доказательства. |
| `completeness` | `state`, `basis`, `reason`, `evidence_refs`. Полнота относится к данному показателю, области и правилу. |
| `calculation` | `policy_id`, поясняющая `formula` и `components[]` с допущенными слагаемыми. Формула предназначена для показа, арифметику выполняет обработчик. |
| `root_issue_id`, `derived_mismatch` | Связь первичной причины с зависимыми расхождениями. `root_issue_id` равен `null` при отсутствии связи. |

Денежная единица MVP `RUB`. Денежное значение передаётся как знаковая десятичная строка с точкой и двумя знаками, например `"123.45"`, `"-8.20"`, `"0.00"`. Знак минус допустим для ненулевых отрицательных значений. JSON-числа, разделители групп, экспоненты, `NaN` и `-0.00` не используются. Расчёт ведётся в `Decimal` либо целых копейках. Сравнение точное в копейках. Политика задаёт единицы, знак и округление, а UI отображает полученные строки. Для поддерживаемого итога XLSX обработчик считает по исходным ячейкам с явной политикой. При неизвестной формуле или пустом кэше без такого правила значение остаётся неизвестным. Для показателей с другой единицей применяются точные десятичные строки с точностью из правила показателя. При отсутствии правила показатель остаётся `unverified`.

`completeness.state` принимает `complete`, `incomplete` и `unknown`. `basis` принимает `manifest`, `user_declaration`, `dataset_fixture` или `none`. При `complete` обработчик указывает, какой состав требовался для этого показателя и чем подтверждено покрытие. Манифест должен описывать ожидаемый состав, включая период или операции, а не только перечислять загрузки. Заявление пользователя используется как явная предпосылка и показывается вместе с результатом. `dataset_fixture` применим к конкретному тестовому профилю без готовых сумм. `none` означает `unknown`. Отсутствие читаемого обязательного файла, неоднозначность роли документа или отсутствие части периода могут оставить полноту `incomplete` либо `unknown`. Полнота сводного показателя не переносится на детализацию.

| Статус | Условие |
| --- | --- |
| `verified` | `complete`, оба значения подтверждены и сопоставимы, `delta = "0.00"` для денег. |
| `discrepancy` | `complete`, оба значения подтверждены и сопоставимы, `delta` ненулевая. Причина и доказательства видны в результате. |
| `unverified` | Отсутствует подтверждённое отчётное или ожидаемое значение, сопоставимость либо полнота. `delta = null`, известные значения и слагаемые сохраняются. |

В `reasons[]` поле `code` различает, например, `amount_mismatch`, `missing_evidence`, `ambiguous_relation` и `unreadable_report_value`. `message` объясняет причину, а `evidence_refs` ведёт к доступным основаниям. Причина отсутствия документа может иметь пустой список ссылок. Для подтверждённой строки без замечаний `reasons` пуст.

В `summary` сохраняются `counts` по трём статусам, `primary_issues` и `conclusion`. Счётчики отражают строки, а первичные причины учитываются по `root_issue_id`. Если одна причина влияет на статью и общий итог, итоговая строка отмечается `derived_mismatch: true` с тем же ID. Сводка отдельно показывает обнаруженные расхождения и непроверенные части. Вывод о совпадении допустим для явно заданной области, где все строки проверены.

## Адреса доказательств и допуск суммы

`evidence` содержит `id`, `document_id`, `kind`, `raw_value`, `normalized_value`, `unit`, `method` и `locator`. `kind` различает `reported_value`, `amount`, `contract`, `period`, `article` и `document_identity`. `method` указывает происхождение, например `native` или `ocr`. `raw_value` показывает исходное написание фрагмента в локальном результате, `normalized_value` содержит проверенное значение соответствующего типа. Для дат используются ISO `YYYY-MM-DD` и явные границы периода, где они известны. Месяц может быть представлен диапазоном, когда источник действительно описывает месяц. Дата документа хранится с собственной ролью и требует правила, прежде чем использовать её как период операции.

| Формат | `locator` |
| --- | --- |
| PDF | `kind: "page"`, `page` от 1 и проверенный адрес фрагмента. Это может быть `bbox`, воспроизводимая строка `line` от 1, пара `table_row` и `table_column` от 1 в однозначно определяемой таблице страницы или другой адрес, по которому однозначно находится фрагмент. |
| PNG | `kind: "page"`, `page: 1` и проверенный адрес фрагмента по тем же правилам. |
| XLSX | `kind: "sheet"`, точное имя `sheet` и `range` в A1-нотации, например `"C6"` или `"C6:C7"`. Адреса исходных слагаемых сохраняются отдельно от ячейки формулы. |
| DOCX | `kind: "paragraph"` и `paragraph`, либо `kind: "table_cell"`, `table`, `row`, `cell`. Индексы от 1 в сохранённом документе, в порядке обхода его структуры. |

`bbox` имеет вид `[x0, y0, x1, y1]` в диапазоне `[0, 1]` с началом слева сверху относительно целой страницы в ориентации, используемой просмотрщиком. Прямоугольник имеет положительные ширину и высоту. Адаптер переводит координаты фрагмента к оригиналу с учётом обрезки, масштаба и поворота, затем делит горизонтальные и вертикальные координаты на размеры страницы. Без проверенной рамки `bbox` равен `null`. Номер строки должен воспроизводиться на сохранённой версии извлечения того же файла. Если строка содержит несколько возможных значений, нужен адрес ячейки, рамка или другой однозначно воспроизводимый адрес значения. Номер страницы служит для навигации. Наблюдение с одним номером страницы не включается в `evidence` и не подтверждает отчётное значение или слагаемое. Если других доказательств нет, зависимое значение остаётся неизвестным. Адреса и ссылки на `evidence` проверяются в границах задания до публикации результата.

Каждый допущенный элемент `calculation.components` содержит `amount`, `amount_refs`, `contract_refs`, `period_refs`, `article_refs` и `relation_reason`. Ссылки подтверждают разные утверждения. Один фрагмент может поддерживать несколько ролей только если из него читаются все соответствующие утверждения. `relation_reason` объясняет применение правила и сопоставление с договором, периодом и статьёй. Для классификации статьи источник может описывать назначение работ без буквального названия статьи. В этом случае нужно понятное правило связи и адрес описания. Одна рамка с суммой подтверждает только значение. Сумма с неопределённым договором, периодом или статьёй остаётся кандидатом в доказательствах и причинах строки. Она не входит в расчёт. `observed_evidence_sum` рассчитывается из допущенных слагаемых один раз, без повторного учёта итогов, составляющих и побайтовых копий.

## Граница с переданным ML-модулем

Worker передаёт `DocumentInput` с `id`, `source_path`, `source_sha256`, `acquisition`, `lines` и необязательным `prediction`. `lines` содержит текст и доступные `page`, `line`, `sheet`, `cell`, `bbox`, `score`, `image`. `source_path` выбирается из локального хранилища задания. При несовпадении байтов с заявленным SHA модуль возвращает `source_changed`, а при недоступности файла `source_unavailable`. Адаптер связывает эти ошибки с ID документа и учитывает их влияние на полноту каждой затронутой строки. Некорректный вход `InputError` фиксируется отдельно от ошибки чтения файла. [Фактический Python API](../backend/ml_module/src/doccheck_ml/api.py)

Результат `doccheck-ml-identity/1` предоставляет `records`, `groups`, `review_queue` и `errors`. В записи `source_facts` и `fact_evidence` дают кандидаты на адресные наблюдения. Адаптер проверяет роль реквизита, нормализованное значение и адрес. `fact_conflicts` и `review_queue` сохраняют неоднозначность. `facts.amount` может содержать произвольную строку из `prediction.amount`, а предложения модели не допускаются в слагаемые без подтверждения. Отсутствие исходного значения и конфликт сохраняются как неизвестное. Группы публичного API автоматически объединяют только одинаковые SHA-256. Отличающиеся байты с похожими реквизитами могут дать `candidate` с `auto_merge=false`. [Аудит NRT-92](ml-module-audit.md)

`process_documents` принимает уже извлечённые наблюдения. Код этой функции не выполняет OCR, разбор КФЗ, финансовую агрегацию и присвоение `verified` или `discrepancy`. Опциональный `QwenReader` возвращает предложенное чтение фрагмента номера и строки. Реальный inference, ресурсы и офлайн-запуск ещё предстоит проверить. В PR #8 открыты три P2 про дату договора вместо даты документа, принятие усечённого номера и потерю отрицательного итога. В затронутых наблюдениях нужны отдельные проверки роли даты, полноты номера и знака суммы перед допуском. Если подтверждения нет, зависимая строка получает `unverified`. Ночной режим `ML: no_training`. [Аудит и воспроизведения](ml-module-audit.md#подтверждённые-дефекты-исходной-версии) · [NRT-93](https://linear.app/andreiakimov/issue/NRT-93/soglasovat-interfejs-ml-modulya-i-rezultat-obrabotki)

## Синтетические примеры

В примерах использованы вымышленные суммы, реквизиты и адреса. Фрагмент `rows[0]` показывает сравнение при полной первичке и принадлежит результату с `synthetic: true`. В полном `CheckResult` каждый ID документа и ссылки разрешаются в реестр этого же задания.

```json
{
  "id": "demo-row-a",
  "label": "Синтетическая статья A",
  "indicator_code": "DEMO-A",
  "unit": "RUB",
  "reported_value": "150.25",
  "reported_evidence_refs": ["ev-report-a"],
  "expected_value": "120.25",
  "observed_evidence_sum": "120.25",
  "delta": "30.00",
  "status": "discrepancy",
  "completeness": {
    "state": "complete",
    "basis": "dataset_fixture",
    "reason": "В синтетическом профиле ожидается одна операция, покрытая источником",
    "evidence_refs": ["ev-demo-contract", "ev-demo-period", "ev-demo-article"]
  },
  "calculation": {
    "policy_id": "demo-sum/1",
    "operation": "sum",
    "formula": "Сумма допущенных операций",
    "components": [{
      "amount": "120.25",
      "amount_refs": ["ev-demo-amount"],
      "contract_refs": ["ev-demo-contract"],
      "period_refs": ["ev-demo-period"],
      "article_refs": ["ev-demo-article"],
      "relation_reason": "Договор и период совпали, назначение отнесено к статье правилом профиля"
    }]
  },
  "reasons": [{"code": "amount_mismatch", "message": "Отчётное значение выше ожидаемого", "evidence_refs": ["ev-report-a", "ev-demo-amount"]}],
  "root_issue_id": "demo-issue-a",
  "derived_mismatch": false
}
```

| Сценарий | `reported_value` | `observed_evidence_sum` | `expected_value` | `delta` | Статус и основание |
| --- | --- | --- | --- | --- | --- |
| Источник явно подтверждает ноль, состав полный | `"0.00"` | `"0.00"` | `"0.00"` | `"0.00"` | `verified`, есть допущенное слагаемое ноль |
| Доступное слагаемое совпало с отчётом, часть периода отсутствует | `"120.25"` | `"120.25"` | `null` | `null` | `unverified`, неполная первичка |
| Найдено число без подтверждения статьи | `"150.25"` | `null` | `null` | `null` | `unverified`, число остаётся кандидатом |
| Полный ожидаемый итог известен, значение КФЗ не прочитано | `null` | `"120.25"` | `"120.25"` | `null` | `unverified`, причина относится к отчёту |

Условные доказательства для фрагмента выше показывают, как адреса поддерживают разные утверждения. Они ссылаются на два синтетических документа `demo-report` и `demo-support`.

| `id` | `kind` | `document_id` | `normalized_value` | `locator` |
| --- | --- | --- | --- | --- |
| `ev-report-a` | `reported_value` | `demo-report` | `"150.25"` | `{"kind":"page","page":1,"bbox":[0.2,0.4,0.5,0.45]}` |
| `ev-demo-amount` | `amount` | `demo-support` | `"120.25"` | `{"kind":"sheet","sheet":"Синтетика","range":"C6"}` |
| `ev-demo-contract` | `contract` | `demo-support` | `"DEMO-K1"` | `{"kind":"sheet","sheet":"Синтетика","range":"A2"}` |
| `ev-demo-period` | `period` | `demo-support` | `{"start":"2025-02-01","end":"2025-02-28"}` | `{"kind":"sheet","sheet":"Синтетика","range":"A3"}` |
| `ev-demo-article` | `article` | `demo-support` | `"DEMO-A"` | `{"kind":"sheet","sheet":"Синтетика","range":"A6"}` |

Адрес ячейки DOCX может выглядеть как `{"kind":"table_cell","table":1,"row":2,"cell":2}`. Полный синтетический результат и машинная схема той же версии находятся в [контракте NRT-86/NRT-18](../contracts/README.md).

У синтетического PNG со строками и денежными колонками `{"kind":"page","page":1,"bbox":null}` открывает страницу. Сумма без другого источника остаётся `null`. Адрес `{"kind":"page","page":1,"bbox":null,"table_row":3,"table_column":4}` пригоден для доказательства, если таблица однозначна и эта ячейка проверена. Для текстового PDF `{"kind":"page","page":1,"bbox":null,"line":7}` пригоден, если сохранённое извлечение воспроизводит строку и однозначно указывает на значение.

Два экземпляра синтетической ведомости имеют одинаковый SHA. В выбранном XLSX разные допустимые операции подтверждены ячейками `C6` и `C7`, обе на `"60.25"`. Договор, период и статья подтверждены для обеих операций. В `calculation.components` остаются два слагаемых, `observed_evidence_sum` равен `"120.50"`. Второй экземпляр остаётся в `documents` с `duplicate_of` на выбранный файл.

## Ограничения к утренней проверке

ТЗ требует по каждой строке показать отчётное значение, ожидаемое при достаточных данных, расхождение, подтверждающий фрагмент и сводку. Разрешённый комплект содержит скан КФЗ с многоуровневой шапкой, документы с нативным текстом и сканы, месячные ведомости с отдельными полями периода, сумм и статей, а также DOCX с реквизитами в абзацах и суммами в таблицах. Два README задают область, но граница периода в карточке и описание комплекта расходятся. До предметного решения сохраняются выбранные пользователем границы и основание. При неоднозначном выборе зависимый результат остаётся `unverified`.
