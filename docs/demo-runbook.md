# Трёхминутное демо DocCheck

Сценарий для подготовки выступления. Три минуты — время выступления.
Время обработки, точность и экономия
требуют отдельного измерения на известной выборке.

## До выступления

- Откройте [готовый синтетический результат](https://doccheck-five.vercel.app/checks/synthetic-example)
  и перезагрузите вкладку. Открытие примера не создаёт задания.
- Для отдельного показа очереди откройте [состояние системы](https://doccheck-five.vercel.app/system-status)
  и проверьте [health](https://doccheck-five.vercel.app/health). Сверьте
  версию текущего Vercel-деплоя и Render-сервиса с записью о публикации
  и укажите её в журнале прогона вместе с URL. Когда страница покажет,
  что API и PostgreSQL доступны, нажмите «Создать синтетическое задание».
  Запишите ID из поля «Задание» и убедитесь, что именно этот ID перешёл
  в `completed`. Выполните шаг до выступления. При недоступности страницы
  оставьте в показе только готовый результат или локальный резерв.
- Подготовьте отдельную вкладку с локальным резервом. Если облачная
  вкладка результата не готова к началу, покажите локальную копию.
- Проведите репетицию с таймером и подготовьте локальную запись с
  синтетическими данными. Перед выступлением откройте запись с отключённой
  сетью и проверьте, что читаются таблица и адреса. Репетиция и запись
  остаются отдельными действиями.

### Предыдущие проверки

14.11.2026 на нескольких версиях синтетического демо проверили открытие и
перезагрузку результата, работу отдельных элементов интерфейса и завершение
синтетических заданий. [Детали прошлых проверок](agent-runs/public-case-review.md#исторические-проверки-демо).
Эти прогоны не заменяют проверку текущего развёртывания перед выступлением.

## Сценарий выступления

| Время | Что показать и сказать |
| --- | --- |
| 0:00–0:25 | Главный бухгалтер или заместитель сверяет карточку фактических затрат (КФЗ) с первичными документами. В рабочем сценарии он передаёт КФЗ и первичку, а приложение собирает сопоставимые сводные значения и показывает основания. Сегодня открыт готовый синтетический результат. |
| 0:25–1:15 | На вкладке «Результат» прокрутите до «Показатели отчёта» и раскройте «Синтетическая статья A». В КФЗ 150,50, подтверждено 120,50, разница 30,00 RUB. Покажите адрес отчётного значения на странице 1 и адреса двух слагаемых по 60,25 в ячейках C6 и C7 листа «Синтетика». В готовом примере доступны адреса, а оригиналы недоступны. [Синтетический результат](../contracts/check-result.v1.synthetic.json) |
| 1:15–1:55 | Перейдите к статье B. Отчётное значение равно 0,00, а полная ожидаемая сумма и дельта отсутствуют, потому что источник не прочитан. Покажите причину непроверенности рядом с первичным расхождением. Это две разные ситуации для разбора бухгалтером. |
| 1:55–2:30 | Вернитесь вверх той же вкладки «Результат» к блоку «Вывод по проверке». Откройте соседнюю вкладку «Документы», чтобы показать решения по файлам. Для сохранённой проверки на этой вкладке доступна кнопка «Скачать XLSX» с выгрузкой показателей и адресов. В готовом примере выгрузки нет. Итоговое решение принимает бухгалтер. |
| 2:30–3:00 | Следующий шаг — полный и повреждённый пакеты через реальный обработчик и независимая оценка. Затем можно согласовать ограниченный пилот на разрешённых данных в вузе. [Два пакета для приёмки](case/use-cases.md) · [План пилота](pilot-roadmap.md) |

## Локальный резерв готового результата

На компьютере показа заранее установите Node.js и зависимости по
[инструкции frontend](../frontend/README.md). Выполните из `frontend/`
с закреплённой версией pnpm:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm exec vite preview --host 127.0.0.1 --port 56553 --strictPort
```

Откройте [локальный готовый результат](http://127.0.0.1:56553/checks/synthetic-example).
Для него достаточно сборки интерфейса. Если нужен отдельный показ
синтетической очереди, заранее поднимите Compose по [инструкции](../README.md#запуск-каркаса-через-docker-compose).
[Чистый запуск в CI](agent-runs/nrt-45-clean-start.md) подтверждает миграции,
синтетический цикл и сохранение результата после повторного запуска.

## Сквозная проверка после готовности обработчика

После подтверждения обработчика в выделенной локальной среде пройдите
[сценарии сверки](case/use-cases.md): загрузите указанный пакет, дождитесь
нового результата через API → worker → обработчик → PostgreSQL → UI и запишите
ID задания и версии входа, обработчика и правил.
Для повреждённого акта проверьте `unverified`, конкретную ошибку и
наблюдаемую сумму, а также источники оставшихся слагаемых. Для изменённого
разрешённого входа заранее задайте ожидаемое изменение и проверьте новый
расчёт после сброса кеша, если он используется. Откройте сохранённый
результат повторно и проверьте XLSX. В выступление этот сценарий включается
после подтверждённого прогона.

Замер исполнения проводится отдельно. Для каждого прогона указываются
состав и размер выборки, версия, оборудование, состояние кеша, интервал
измерения и исход. Качество оценивается на независимых ожиданиях с описанием
пропущенных расхождений и ложных подтверждений.
