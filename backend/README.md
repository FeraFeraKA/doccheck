# Python backend

Backend включает FastAPI, PostgreSQL и **отдельные Python worker-процессы**.
Стандартный каркас Compose проверяет жизненный цикл на синтетических заданиях
и не обрабатывает загруженные документы. Для отдельного локального пути
доступен адаптер v3.2; его возможности и ограничения описаны в
[архитектуре](../docs/architecture.md). Переданный
[ML-модуль](ml_module/README.md) остаётся отдельным пакетом; каркас не
устанавливает его зависимости и веса.

## Docker Compose

[Команды запуска](../README.md#запуск-каркаса-через-docker-compose) выполняются
из корня репозитория. Compose собирает один образ Python для API, worker и
одноразовой миграции. После проверки PostgreSQL сервис `migrate` выполняет
`alembic upgrade head`. API и worker стартуют после успешной миграции, а
frontend ждёт успешного `/health` API. Ошибка миграции останавливает запуск
зависимых сервисов.

Compose формирует `DATABASE_URL` для хоста `db` из `DOCCHECK_DB_PASSWORD`.
Переменная `DATABASE_URL` в `.env` ниже используется для локального запуска
без контейнеров. Используйте буквы и цифры в пароле Compose, чтобы его можно
было подставить в URL. PostgreSQL использует пароль при первичной инициализации
тома. Изменение `.env` само по себе не меняет пароль уже созданной роли.

PostgreSQL 18 хранит данные в именованном volume `postgres-data`,
подключённом к `/var/lib/postgresql`. API принимает КФЗ и первичные документы
через `POST /api/v0/runs` и сохраняет оригиналы в именованном томе
`run-files`. При штатном запуске Compose задания с документами остаются
в `queued` до запуска отдельного документного worker.
Список разрешённых путей в `.dockerignore` исключает `data/`, `.env`,
примеры, holdout и ML-модуль с весами из контекста сборки. Рабочий пароль
передаётся сервисам при запуске и не входит в образ.

## Установка и PostgreSQL

Нужны Python **3.12.12** (`.python-version`), uv **0.9.17** и локальный
PostgreSQL. В Compose используется PostgreSQL **18.4**. Python при
необходимости может загрузить uv. Из `backend/`:

```sh
uv sync --frozen
```

Прямые зависимости закреплены в `pyproject.toml`, полное дерево — в `uv.lock`.
Подготовьте отдельную БД и пользователя PostgreSQL. Например, от имени локального
администратора:

```sh
createuser -h 127.0.0.1 -U postgres --pwprompt doccheck
createdb -h 127.0.0.1 -U postgres --owner=doccheck doccheck
```

Скопируйте корневой `.env.example` в `.env` и замените `CHANGE_ME` локальным
паролем. При необходимости URL-кодируйте пароль. `.env` исключён из Git.
API, worker и Alembic используют этот файл; переменные процесса имеют приоритет.

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Обязательный URL вида `postgresql+psycopg://user:password@host:port/database` |
| `WORKER_POLL_SECONDS` | Ожидание пустой очереди: по умолчанию `0.5`, от `0.05` до `60` секунд |
| `SYNTHETIC_DELAY_SECONDS` | Искусственная задержка для наблюдения статусов: по умолчанию `2`, от `0` до `60` секунд |

Из `backend/` примените миграцию:

```sh
uv run --frozen alembic upgrade head
```

Миграции создают `synthetic_jobs`, `runs` и служебную `alembic_version`
в выбранной БД.
Повторное применение сохраняет задания. API не меняет схему при запуске:
`/health` вернёт 503, если PostgreSQL или таблица заданий недоступны.

## Запуск

API и worker запускаются в **разных терминалах** из `backend/`:

```sh
uv run --frozen uvicorn doccheck_backend.api:app --host 127.0.0.1 --port 8000
```

```sh
uv run --frozen python -m doccheck_backend.worker
```

В третьем терминале, из `frontend/`:

```sh
pnpm install --frozen-lockfile
pnpm dev --host 127.0.0.1
```

Откройте адрес Vite для мастера проверки. Технический цикл синтетического
worker доступен через `POST /api/synthetic-jobs` и последующий
`GET /api/synthetic-jobs/{id}`. Без worker задание останется в очереди.
Vite направляет `/health` и `/api` на порт 8000; другую цель задаёт
`DOCCHECK_API_TARGET` (см. [frontend README](../frontend/README.md)).
Компоненты останавливаются по Ctrl+C; задания сохраняются в PostgreSQL.

Чтобы обработать не более одного задания и выйти:

```sh
uv run --frozen python -m doccheck_backend.worker --once
```

Один worker обрабатывает задания последовательно. Короткая транзакция с
`FOR UPDATE SKIP LOCKED` резервирует задание и сохраняет `processing`. Обработка
идёт после её завершения, а `completed` записывается вместе с результатом.
Синхронные маршруты FastAPI выполняют только короткие операции БД.

## Жизненный цикл сохранённых пакетов

`POST /api/v0/runs` сохраняет пакет и создаёт запись `runs` со статусом
`queued`. Запуск `python -m doccheck_backend.worker` обслуживает синтетический
каркас. Очередь пакетов имеет отдельную команду. Из `backend/`:

```sh
uv run --frozen python -m doccheck_backend.run_worker --processor my_local_adapter:process
```

`my_local_adapter:process` обозначает доверенный локальный модуль и его
функцию, доступные в окружении Python. Подготовьте и укажите адаптер для
обработки пакетов. Без него принятые пакеты ожидают в очереди. Ошибка
загрузки адаптера завершает команду до захвата заданий. Опция `--once`
ограничивает процесс одним заданием.

### Сверка с Qwen и LoRA в WSL

Для локальной загрузки КФЗ и первичных документов запустите отдельный
документный worker v3.2 в WSL 2 с Ubuntu 24.04, Python 3.12 и доступной
из WSL видеокартой NVIDIA с поддержкой CUDA 12. Подготовьте локальный
PostgreSQL по инструкции выше и задайте `DATABASE_URL` в корневом файле
`.env`. API и worker должны использовать одну базу и одну папку загрузок.
По умолчанию это каталог `data/runs` репозитория.

В терминале WSL из корня репозитория:

```sh
sudo apt install python3.12-venv tesseract-ocr-rus tesseract-ocr-eng libgl1 libglib2.0-0t64
python3.12 -m venv data/venv-v32
data/venv-v32/bin/python -m pip install -r backend/requirements-v32-cuda.lock
data/venv-v32/bin/python -m pip install --no-deps -e ./backend -e ./backend/ml_module
data/venv-v32/bin/python -m pip check
data/venv-v32/bin/python -m alembic -c backend/alembic.ini upgrade head
```

Запустите API и документный worker в разных терминалах WSL из корня репозитория.

```sh
data/venv-v32/bin/python -m uvicorn doccheck_backend.api:app --host 127.0.0.1 --port 8000
```

```sh
export DOCCHECK_QWEN_MODEL_DIR=/path/to/local-qwen-model
export DOCCHECK_QWEN_ADAPTER_PATH=/path/to/local-adapter/checkpoint.safetensors
PYTHONPATH="$PWD" data/venv-v32/bin/python -m doccheck_backend.run_worker --v32
```

В каталоге модели должен быть `model.safetensors`, рядом с выбранным
чекпойнтом LoRA — `adapter_config.json`. Подготовьте совместимые веса на
машине с worker. `PYTHONPATH` даёт worker доступ к модулям сверки в
`bench/` текущей рабочей копии.

В третьем терминале из корня запустите интерфейс:

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev --host 127.0.0.1
```

Откройте адрес Vite и загрузите КФЗ с первичкой. Worker определит строку
КФЗ по скану и выполнит сверку по загруженному комплекту. При неоднозначной
строке откройте из карточки проверки ручной выбор для уже загруженного
комплекта. Для штатного профиля Compose выбор обработчика остаётся явной
настройкой.

### Отдельный документный worker в Compose

Обычный `docker compose up --build --wait` запускает синтетический worker.
Сохранённые пакеты ждут отдельного сервиса `document-worker`. Когда доверенный
адаптер установлен в локальном образе с backend DocCheck, задайте в `.env`
`DOCCHECK_DOCUMENT_WORKER_IMAGE` с его именем и `DOCCHECK_DOCUMENT_PROCESSOR`
в форме `module:callable`. Из корня репозитория запустите сервис явно.

```sh
docker compose up --build --wait
docker compose --profile document-worker up -d document-worker
docker compose logs document-worker
```

Профиль использует ту же БД и том пакетов в режиме чтения. При пустом или
неимпортируемом `DOCCHECK_DOCUMENT_PROCESSOR` worker завершается до захвата
заданий. Базовый образ содержит вход `run_worker`, но не включает каталог
`bench/` и зависимости адаптера v3.2. Образ с рабочим адаптером, его
зависимости и доступ к локальной модели нужно подготовить отдельно. Тестовый адаптер
остаётся в `backend/tests/` и исключён из контекста сборки.

Обработчик получает `StoredRun` и каталог файлов пакета. `report_document_id`
указывает на КФЗ в манифесте. `scope` содержит явно заданную область или
`None`, когда область определяет обработчик. В этом случае в PostgreSQL
в поле `runs.scope` хранится пустой объект. Явные области уже сохранённых
заданий читаются в прежнем формате.

Обработчик возвращает `CheckJob` версии 1. Worker проверяет ID задания, ID
и хеши файлов, совпадение КФЗ и совпадение явной области, если она задана.
Область, определённая обработчиком, хранится в `result.scope`. Версия 1
поддерживает одну область на результат. Если обработчик не может её
установить, он может вернуть `failed` с диагностикой и без результата.
Worker атомарно сохраняет итоговое состояние и результат. Частичные ошибки
файлов сохраняются в результате `completed_with_issues`. Верхнеуровневая ошибка адаптера в этом же
состоянии заменяется безопасным признаком `processing_completed_with_issues`.
Необработанное исключение даёт `failed` с безопасной причиной.

Сессионная блокировка PostgreSQL даёт одному процессу право обслуживать
конкретную таблицу `runs`, даже если процессы используют разные пути
поиска схем. Транзакции захвата и завершения короткие. При завершении
сессии PostgreSQL освобождает блокировку. Следующий владелец помечает
оставшиеся `processing` как `failed` с кодом `worker_interrupted`,
затем продолжает обработку `queued`. Бухгалтер может запустить новую
проверку с новым ключом идемпотентности. Зависший процесс освобождает
очередь после остановки и перезапуска. Сохранённые исходные файлы остаются
доступны для дальнейшей работы. Если другой процесс уже владеет очередью,
команда завершится с ошибкой и её можно запустить позже.

Если сессия потеряна во время синхронного вызова адаптера, сам адаптер может
продолжить вычисления до возврата. Запись исхода разрешена через то же
физическое соединение, которое получило блокировку. После потери сессии
нужен новый запуск процесса, который восстановит очередь.

## Синтетический HTTP-интерфейс 0.1.0

Это интерфейс синтетического каркаса. Маршруты документных пакетов описаны
ниже. Источник DTO — `src/doccheck_backend/schemas.py`, OpenAPI доступен в
`/openapi.json` и `/docs` при прямом обращении к API; стандартный frontend
Compose не проксирует эти два адреса.

| Запрос | Ответ |
| --- | --- |
| `GET /health` | 200: `status: ok`, `database: ok`; 503 при недоступной БД или схеме |
| `POST /api/synthetic-jobs` без тела | 201: созданное синтетическое задание в `queued` |
| `GET /api/synthetic-jobs/{UUID}` | 200: задание; 404 для неизвестного ID, 422 для неверного UUID |

Задание содержит UUID, `synthetic: true`, статус, время создания/начала/окончания,
`result` и `error`. До обработки результат равен `null`. Синтетический
результат явно помечен, а сбой обработки даёт `failed` с безопасным кодом.

## Проверки и ограничения

```sh
uv run --frozen ruff check src migrations tests
uv run --frozen ruff format --check src migrations tests
uv run --frozen pytest
```

Задайте `DOCCHECK_TEST_DATABASE_URL` отдельной тестовой БД PostgreSQL:
[tests/README.md](tests/README.md). Без этой настройки проверки БД пропускаются.

После аварийной остановки worker или потери БД при записи задание может
остаться в `processing`. Локальный API принимает пакеты. Обработка пакетов требует
[отдельного документного worker](#отдельный-документный-worker-в-compose)
с подключённым адаптером.

## Приём пакета

Мастер сначала передаёт пакет через `POST /api/v0/runs/uploads`. Пакет
сохраняется в состоянии `prepared`; `POST /api/v0/runs/uploads/{upload_id}/start`
ставит его в очередь. Подробности описаны в
[контракте API](../contracts/doccheck-api.v0.openapi.yaml).

`POST /api/v0/runs` принимает multipart по [OpenAPI v0](../contracts/doccheck-api.v0.openapi.yaml)
и возвращает `202` после сохранения файлов и записи задания в PostgreSQL.
Клиент передаёт UUID `Idempotency-Key`, КФЗ (`report`) и первичные документы
(`documents`). Совместимые старые клиенты передают также все четыре поля
явной области: `contract_number`, `period_start`, `period_end` и
`report_row_locator`. Частичную явную область сервер отклоняет.
При повторе того же пакета с тем же ключом возвращается исходный идентификатор.
При изменении содержимого, порядка, имени или параметров с тем же ключом возвращается
`409`. Для новой отправки нужен новый ключ.

Файлы хранятся под серверными идентификаторами в `DOCCHECK_UPLOAD_ROOT`.
Локальный запуск использует `data/runs` по умолчанию. Compose монтирует
постоянный том `run-files` в API и подключает его к worker только для чтения.
При аварии после перемещения файлов и до подтверждения транзакции может
остаться каталог без записи в БД. Он не попадает в очередь.

## История, состояние и источники

- `GET /api/v0/runs?limit=20` возвращает запуски от новых к старым. Для
  следующей страницы передайте полученный `next_cursor` в параметре `cursor`.
- `GET /api/v0/runs/{run_id}` возвращает состояние, техническую ошибку и
  доступный прогресс. Числовой прогресс известен после приёма пакета и после
  успешного завершения. Во время обработки или после сбоя он может быть `null`.
- `GET /api/v0/runs/{run_id}/findings` возвращает сохранённый результат.
  Для незавершённого задания и задания без результата возвращается `409`
  с кодом `result_pending` или `run_failed`.
- `GET /api/v0/runs/{run_id}/exports/xlsx` выгружает тот же сохранённый
  результат как вложение XLSX. В книге есть итог и показатели сверки, адреса
  доказательств и сведения о документах. Суммы выгружаются текстом с исходной
  точностью. Пустые денежные ячейки обозначают неизвестные значения.
  Для незавершённого задания и задания без результата действуют те же `409`.
- `GET /api/v0/runs/{run_id}/documents/{document_id}` скачивает оригинал
  из пакета указанной проверки. Путь
  `/api/v0/runs/{run_id}/documents/{document_id}/fragments/{evidence_id}`
  возвращает структурное доказательство и его адрес из результата. Кодируйте
  идентификатор для одного сегмента URL. Для произвольного идентификатора
  используйте `GET /api/v0/runs/{run_id}/documents/{document_id}/fragments`
  с параметром `evidence_id`, сформированным через
  `new URLSearchParams({ evidence_id: id })`. Этот вариант сохраняет
  разделители пути и ID `.` и `..` при передаче через браузер и прокси.
  Перед выдачей API сверяет размер и SHA-256 открытого оригинала с манифестом.
  При недоступном или изменённом оригинале документ и его фрагменты получают
  `404`. Хранилище предназначено для неизменяемых загруженных файлов.
  Внешняя запись во время потоковой передачи остаётся за этой границей.

Маршруты читают PostgreSQL и локальное хранилище. Для получения результатов
необходим запущенный документный worker с подключённым адаптером.
