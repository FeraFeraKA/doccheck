# Правила работы с backend

Корневой `AGENTS.md` и `CONTRIBUTING.md` действуют для всего проекта; этот файл дополняет их правилами backend. Николай отвечает за API и интеграцию, Семён — за обработку, модель и OCR; вопросы на границе согласовываются по корневым правилам.

## Архитектура

Использовать компактный модульный backend: единый Python-проект с отдельными входами API и worker, хранением в PostgreSQL и явной границей подключения модуля Семёна. Ранее согласованы FastAPI, SQLAlchemy и Alembic; зависимости и их версии ещё не настроены, совместимость с модулем Семёна предстоит проверить. Это принцип организации, а не требование создать много папок, классов или новых сервисов. Наличие, интерфейс и границы готового модуля проверяются в NRT-92/93.

Разделять обязанности по мере появления кода:

- **API:** FastAPI-маршруты, проверка входа, преобразование ошибок в HTTP-ответы и вызов сценария приложения. Маршрут не содержит OCR, расчёты или длинную обработку.
- **Сценарии приложения и задания:** создание и получение задания, порядок его обработки, переходы состояний и применение проверенного результата. Эти функции можно вызвать из API или worker без зависимости бизнес-логики от HTTP.
- **Worker:** отдельно от API получает задание и запускает обработку; не считать задачу успешной до сохранения фактического результата. Первоначально обрабатывается один пакет за раз; изменение параллельности обосновывается и проверяется отдельно с учётом возможностей модуля.
- **Адаптер модуля:** переводит согласованный вход в формат Семёна и его фактический ответ — в единый контракт. Модуль может вызываться как Python-код или локальный сервис: способ не выбирать до изучения реализации. Не дублировать внутри backend уже работающие извлечение, OCR и расчёты без необходимости.
- **Хранение:** PostgreSQL для заданий и результатов, файлы — в согласованном локальном хранилище. Доступ к БД и файлам отделять от маршрута и правил обработки; имена пользователей не использовать как произвольные серверные пути.
- **Контракт и предметные данные:** один версионированный источник структуры результата и связанные модели. Не считать присланную JSON Schema 0.1 утверждённой и не создавать несовместимые параллельные схемы. Синтетика помечается; предположение модели не выдаётся за доказанный факт.

Внешние детали — FastAPI, база, файловая система и конкретная ML-реализация — не должны определять правила предметной обработки. Интерфейс между ними делать достаточно явным для подмены в тесте, но не создавать `Protocol`, репозиторий или класс для каждого простого вызова автоматически. Решение о внутреннем устройстве модели и её зависимостях остаётся за Семёном.

## Python и читаемость

- Следовать PEP 8 и существующему форматированию проекта: четыре пробела, `snake_case` для функций и модулей, `PascalCase` для классов, понятные имена по смыслу. Не менять форматирование несвязанного кода.
- Аннотировать параметры и возвращаемые значения публичных функций, обработчиков, интерфейсов интеграций и нетривиальной логики. Подбирать типы по закреплённой версии Python; не использовать `Any` без причины и не скрывать ошибки проверки типов подавлениями без объяснения.
- Функция и класс должны делать понятную работу. Предпочитать явные ветвления и ранний выход сложной вложенности; не выносить одноразовую строку в абстракцию без пользы. Избегать изменяемых значений по умолчанию и побочных действий при импорте модуля.
- Писать docstring, когда он объясняет назначение, условия, ошибки или единицы измерения, не очевидные из кода. Комментарии объясняют причину решения и ограничения, а не повторяют строку кода.
- Перед использованием библиотеки или инструмента сверять закреплённую в проекте версию и относящуюся к ней официальную документацию. Версии Python и backend-зависимостей, линтер и форматтер пока не закреплены; фиксировать их при соответствующей задаче с учётом модуля Семёна.

## Границы API, worker и данных

- Проверять входы и выходы на границах API и адаптера модели по актуальному контракту. Отдельно обрабатывать некорректный ввод, недоступность модуля, ошибки отдельных файлов и технический сбой задания; не возвращать тестовую фикстуру как настоящий результат.
- Деньги считать только через `Decimal` или целые копейки; денежные значения передавать в JSON строками. Не превращать отсутствие значения в ноль и не объявлять частичную сумму полным ожидаемым значением. Источники и основания сопоставления сохранять по контракту.
- Отделять статус задания от статуса показателя и ошибки файла. Долгую GPU/OCR-обработку запускает отдельный worker; при необходимости он обращается к отдельному модулю или сервису. Не выполнять её внутри HTTP-запроса и не заменять worker in-process задачей.
- Использовать `async` для соответствующего неблокирующего I/O, а не как обозначение «быстрого кода». Блокирующие вызовы не должны удерживать event loop; фактический интерфейс модели и способ её запуска проверить отдельно.
- Сессию БД и транзакцию ограничивать соответствующим запросом или единицей работы worker, закрывать ресурсы при успехе и ошибке. Не передавать одну изменяемую сессию между параллельными задачами. Не держать транзакцию открытой на время длительного вызова модели без обоснования.
- Ошибки перехватывать там, где можно добавить контекст или принять решение. Не скрывать исключения общим `except Exception` внутри предметной логики и не выдавать подставленные значения за результат; на границе worker общий перехват допустим для фиксации технической ошибки задания.
- Логи и ошибки должны помогать диагностике без секретов, содержимого документов, OCR-текста и закрытого эталона. Режим данных — `docs/data-policy.md`; не отправлять документы во внешние сервисы по предположению.

## Проверки

Тесты backend размещать в `backend/tests/` и следовать [tests/AGENTS.md](tests/AGENTS.md). Проверять затронутые сценарии и ошибки на синтетических или разрешённых данных; тестовый обработчик не является реальной моделью. Команды и используемые средства фиксировать после их фактической настройки.
