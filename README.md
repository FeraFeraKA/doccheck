# DocCheck

Цель проекта — локальная сверка карточки фактических затрат (КФЗ) с первичными документами: сбор сводных значений, сравнение с КФЗ и показ источников и возможных причин расхождений.

Проект команды **«Буткемперы»**, хакатон МФТИ, трек 5.

## Текущий этап

Синтетический каркас связывает frontend, FastAPI, PostgreSQL и отдельный Python worker. В интерфейсе видно состояние API и прохождение задания через очередь, обработку и завершение. [Настройка БД, миграции и команды запуска](backend/README.md). Тестовый результат явно помечен. Версионированный [контракт результата](contracts/README.md) и синтетический пример находятся в репозитории; HTTP-каркас пока использует временный ответ. Загрузка документов, OCR и финансовая сверка относятся к следующим задачам.

Для подключения к backend доступен [Python-модуль реквизитов и Qwen-reader](backend/ml_module/README.md)
с тестами и синтетическим примером без весов. Он обрабатывает готовые наблюдения
и не заменяет полный конвейер финансовой сверки.

## Структура

```text
backend/             Python: API, worker, обработка и денежная логика
backend/tests/       Тесты backend и инструкции для них
frontend/            TypeScript: пользовательский интерфейс
frontend/tests/      Тесты frontend и инструкции для них
contracts/           Решения по общему контракту после согласования
docs/                Архитектура и правила разработки
data/                Локальные оригиналы, превью и результаты; вне Git
```

## Начало работы

```sh
git clone https://github.com/VCyberPunk2077/doccheck.git
cd doccheck
```

```sh
git diff --check
```

Для приватного репозитория владелец выдаёт участникам доступ; каждый проверяет клонирование под своим аккаунтом. Успешное клонирование владельцем не подтверждает доступ остальных участников.

## Планируемый стек

Frontend: React, TypeScript, Vite, React Router, Zustand, Tailwind CSS и собственные компоненты. Менеджер пакетов — pnpm. Backend: Python/FastAPI, SQLAlchemy, Alembic, отдельный Python worker и PostgreSQL. Миграция создаёт схему синтетических заданий. По целевой архитектуре оригиналы хранятся локально, PostgreSQL хранит задания, метаданные и результаты.

## Запуск каркаса через Docker Compose

Нужны запущенный Docker Engine с Linux-контейнерами и Docker Compose с
поддержкой `up --wait`. Скопируйте `.env.example` в `.env`, если файла ещё
нет, и задайте `DOCCHECK_DB_PASSWORD` случайной строкой из букв и цифр,
например 32 шестнадцатеричными символами. Затем из корня репозитория:

```sh
docker compose up --build --wait
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080) и создайте
синтетическое задание. Если порт занят, задайте `DOCCHECK_PORT` в `.env`.
PostgreSQL проходит проверку готовности, затем отдельный сервис `migrate`
применяет миграцию перед запуском API и worker.

```sh
docker compose ps --all
docker compose down
docker compose up --wait
```

Обычный `down` сохраняет задания в именованном volume PostgreSQL.
`docker compose down --volumes` удалит данные этого проекта. Первичная
сборка получает закреплённые образы и зависимости из реестров. GPU, OCR и
реальный inference относятся к оставшейся части NRT-41.
Подробности конфигурации и версии — в [документации backend](backend/README.md).
